## ۳. یک مثال واقعی با Python

فرض کن این برنامه را داریم:

`app.py`

```python
print("Hello from Docker!")
```

کنارش یک فایل به نام `Dockerfile` می‌سازیم:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY app.py .

CMD ["python", "app.py"]
```

حالا در ترمینال:

```powershell
docker build -t my-python-app .
```

این دستور ایمیج می‌سازد.

بعد:

```powershell
docker run my-python-app
```

برنامه داخل کانتینر اجرا می‌شود و خروجی می‌دهد:

```text
Hello from Docker!
```

## یک چرخهٔ کاری واقعی

مثلاً فرض کن سالون بعد از خطای اتصال یک مدل، پاسخ مدل دیگر را هم از دست می‌دهد.

ایگور می‌تواند:

1. کد مربوط به مدیریت درخواست‌ها را پیدا کند.
2. رفتار فعلی را با یک تست بازتولید کند.
3. علت احتمالی را بررسی کند.
4. تغییر را در شاخهٔ آزمایشی اعمال کند.
5. تست قبلی و تست جدید را اجرا کند.
6. لاگ و Trace را بررسی کند.
7. ببیند آیا پاسخ مدل دوم همچنان حفظ می‌شود.
8. Diff و گزارش نتیجه را ارائه کند.

نکتهٔ مهم این است که **ایگور نباید صرفاً به این نتیجه برسد که کد بدون خطا اجرا شد؛ باید شواهدی داشته باشد که رفتار موردنظر واقعاً درست شده است.**

## سه نوع Trace که به نظرم لازم داریم

| نوع | چه چیزی را نشان می‌دهد؟ |
|---|---|
| Agent Trace | ایگور چه تصمیمی گرفت و چرا؟ چه فایل‌هایی را تغییر داد؟ |
| Execution Trace | برنامه چه مسیری را طی کرد؟ کجا خطا رخ داد؟ |
| Test Trace | چه چیزی آزمایش شد و نتیجه دقیقاً چه بود؟ |

این سه مورد را نباید با هم قاطی کنیم. مثلاً موفقیت تست به معنی درست بودن تصمیم ایگور نیست؛ و اجرای موفق برنامه هم به معنی صحت رفتار آن نیست.

## یک تصمیم معماری مهم

من چهار سطح اختیار برای ایگور در نظر می‌گیرم:

- **خواندن:** بررسی فایل‌ها و کد.
- **آزمایش:** اجرا و تست بدون تغییر نسخهٔ اصلی.
- **تغییر:** ویرایش کد در محیط آزمایشی و تکرار تست.
- **انتشار:** ادغام تغییرات در نسخهٔ اصلی.

سه سطح اول می‌توانند به‌تدریج خودکار شوند؛ انتشار باید اختیار جداگانه‌ای داشته باشد.

### یک نکتهٔ فنی که نباید اشتباه بگیریم

Docker به‌تنهایی به ایگور توانایی ویرایش فایل نمی‌دهد. ما به یک **Local Agent Runner** روی ویندوز نیاز داریم؛ برنامه‌ای که به ایگور ابزارهای مشخصی بدهد:

- خواندن و نوشتن فایل‌ها
- اجرای دستورهای PowerShell یا دستورات داخل کانتینر
- مدیریت Git و شاخه‌های آزمایشی
- اجرای تست‌ها
- جمع‌آوری خروجی و Trace

این Runner واسطهٔ بین ایگور و محیط توسعه است. خود ایگور لازم نیست مستقیماً به تمام ویندوز دسترسی داشته باشد.

### سه قاعده‌ای که از ابتدا می‌گذارم

1. نسخهٔ اصلی پروژه دست‌نخورده بماند؛ تغییرات در Worktree یا شاخهٔ جدا انجام شوند.
2. ایگور بتواند چند دور اصلاح و تست را مستقل انجام دهد، ولی نتواند بی‌اجازه تغییرات را وارد نسخهٔ اصلی کند.
3. تمام اقداماتش ثبت شوند؛ حتی تغییر ناموفق، تست شکست‌خورده و اصلاحی که بعداً برگشت داده شده است.

گزارش هم باید چیزی بیشتر از «موفق شد» باشد. مثلاً:

| گزارش | نمونه |
|---|---|
| فایل تغییرکرده | `saloon_web_v4.py` |
| نوع تغییر | اصلاح مدیریت خطای شبکه |
| تست اجراشده | `test_resilience.py` |
| نتیجه | ۱۲ موفق، ۱ ناموفق |
| اصلاح مجدد | انجام شد |
| وضعیت نهایی | هنوز نیازمند بررسی |

## قبل از هر تغییری، سه بررسی

PowerShell را با دسترسی Administrator باز کن و این دستورها را اجرا کن:

**۱. بررسی فهرست توزیع‌های قابل نصب**
```powershell
wsl --list --online
```

**۲. بررسی نسخهٔ WSL نصب‌شده از Microsoft Store**
```powershell
Get-AppxPackage *WindowsSubsystemForLinux* | Select-Object Name, Version, PackageFullName
```

**۳. بررسی سرویس WSL**
```powershell
Get-Service LxssManager
```

خروجی‌ها را بفرست.

چرا این سه مورد؟ چون می‌خواهم بفهمم آیا باید WSL را به نسخهٔ جدیدتر ارتقا بدهیم، یا مستقیماً بستهٔ Ubuntu را به روش دستی نصب کنیم. مایکروسافت هر دو مسیر را مستند کرده است. <Link url="https://learn.microsoft.com/en-us/windows/wsl/install-manual" title="راهنمای نصب دستی WSL"/>.

فعلاً نه ویندوز را تعمیر می‌کنیم، نه چیزی را حذف می‌کنیم، نه دوباره Ubuntu را نصب می‌کنیم.

🚀 ایلان هنوز اجازهٔ ورود به آزمایشگاه ندارد؛ فعلاً داریم با نگهبان در ورودی مذاکره می‌کنیم! 🤣

خب، این خروجی سه نکتهٔ مهم را روشن کرد:

1. **فهرست توزیع‌های WSL در دسترس است.** پس فرمان `wsl --list --online` کار می‌کند و WSL می‌تواند کاتالوگ توزیع‌ها را دریافت کند.
2. **بستهٔ Store برای WSL نصب‌شده دیده نمی‌شود.** دستور `Get-AppxPackage` هیچ خروجی نداشته؛ یعنی برای حساب فعلی بسته‌ای با این نام پیدا نشده است.
3. **سرویس قدیمی WSL فعال است.** `LxssManager` در وضعیت `Running` قرار دارد.

بنابراین فعلاً شواهد بیشتر به سمت استفاده از نسخهٔ قدیمی‌تر و داخلی WSL می‌روند؛ اما هنوز علت خطای `0x8000ffff` را قطعی نمی‌دانیم. نکتهٔ خوب این است که لازم نیست فعلاً سراغ تعمیر ویندوز یا نصب مجدد برویم.

**قدم بعدی:** در همین PowerShell که با دسترسی Administrator باز کرده‌ای، این دستور را اجرا کن:

```powershell

```

این دستور تلاش می‌کند هسته و اجزای WSL را به‌روزرسانی کند. اگر موفق شد، خروجی‌اش را بفرست؛ اگر گفت فرمان یا گزینه شناخته‌شده نیست، آن هم اطلاعات تشخیصی مفیدی است.

فعلاً Ubuntu را دوباره نصب نکن. اول می‌خواهیم وضعیت خود WSL را درست کنیم، بعد سراغ توزیع لینوکس برویم. 😄

| **PS C:\Windows\system32> wsl --update**<br>**Installing: Windows Subsystem for Linux**<br>**Catastrophic failure**<br>**PS C:\Windows\system32>** |
| :--- |

خب، این بار خودِ دستور به‌روزرسانی هم با **Catastrophic failure** متوقف شده. این دیگر فقط مشکل نصب Ubuntu نیست؛ مسیر به‌روزرسانی خود WSL هم شکست می‌خورد.

اما یک نکته مهم: هنوز نمی‌توانیم بگوییم فایل‌های ویندوز خراب‌اند. طبق راهنمای مایکروسافت، `0x8000ffff` خطای عمومی است و چند علت احتمالی دارد. <Cite refs={["turn172111search0"]}/>

قبل از هر تعمیر یا نصب مجدد، می‌خواهم یک بررسی دیگر انجام دهیم.

### پیشنهاد من: عبور از مسیر Store و نصب دستی هستهٔ WSL2

مایکروسافت برای همین شرایط مسیر نصب دستی دارد. این مسیر به نصب بستهٔ جدید WSL از Store وابسته نیست. <Cite refs={["turn645053search0","turn645053search4"]}/>

**مرحلهٔ اول — نصب هستهٔ WSL2**

از لینک رسمی مایکروسافت فایل نصب را دریافت کن:

[دانلود WSL2 Linux Kernel Update x64](https://wslstorestorage.blob.core.windows.net/wslblob/wsl_update_x64.msi)

<text color="secondary" size="sm">این فایل مخصوص پردازنده‌های x64 است؛ سیستم تو نیز x64 است.</text>

1. فایل MSI را اجرا کن.
2. اگر درخواست دسترسی Administrator کرد، تأیید کن.
3. اجازه بده نصب کامل شود.

**فعلاً Ubuntu را نصب نکن.**

بعد از نصب، در PowerShell این دستور را اجرا کن:

```powershell
wsl --set-default-version 2
```

اگر پیام موفقیت دریافت کردی، خروجی را بفرست.

این مرحله مشخص می‌کند آیا می‌توانیم بدون نصب Store WSL، از نسخهٔ داخلی ویندوز به‌همراه هستهٔ WSL2 استفاده کنیم یا نه.

به نظرم فعلاً بهتر است به‌جای جنگیدن با نصب‌کنندهٔ خراب، از مسیر رسمی جایگزین عبور کنیم. 😁

عالی! 😁 این مرحله با موفقیت انجام شد.

اما دقت کن: این هنوز اثبات نمی‌کند که هستهٔ WSL2 واقعاً نصب و آمادهٔ اجراست.
