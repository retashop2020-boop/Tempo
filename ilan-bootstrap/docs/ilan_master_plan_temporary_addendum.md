# الحاقیهٔ موقت برای سند اصلی پروژهٔ ایلان
## یادداشت‌های بررسی زیرساخت و Runner

**مبنای الحاق:** نسخهٔ ۰.۳ سند `ilan_new_workbench_master_plan.md`  
**وضعیت:** پیش‌نویس موقت برای ادغام بعدی؛ هنوز به سند اصلی یا Library اضافه نشده است.

---

## ۱. هدف این الحاقیه

ثبت یافته‌های بررسی فنی اخیر دربارهٔ سه بخش `ilan-workbench`، `ilan-bootstrap` و `runner` تا هنگام ادغام در نسخهٔ بعدی سند اصلی، تصمیم‌ها و شواهد این مرحله از بین نروند.

این یادداشت، جایگزین سند اصلی نیست و به‌تنهایی تصمیم معماری نهایی جدیدی ایجاد نمی‌کند.

## ۲. وضعیت مسیرهای محلی بررسی‌شده

| مسیر | وضعیت مشاهده‌شده |
|---|---|
| `~/ilan-lab/ilan-workbench` | میزکار جدید؛ ساختار اولیه شامل `inbox`، `workspace`، `outbox` و `logs` و فایل راهنما ایجاد شده است. |
| `~/ilan-lab/ilan-workspace` | در بررسی قبلی خالی گزارش شده است. |
| `~/ilan-lab/ilan-bootstrap` | کدهای عامل/نسل جدیدتر در این مسیر قرار دارند؛ مسیر فعلی در بررسی Git مستقل، مخزن Git تشخیص داده نشد. |
| `~/ilan-lab/runner` | مخزن Git مستقل و دارای اجزای هسته‌ای امنیت، عملیات، اجرا، Trace، Workspace و ابزارهای فایل است. |

**احتیاط:** نبودن `.git` در خود پوشهٔ `ilan-bootstrap` فقط ثابت می‌کند که این مسیر در بررسی انجام‌شده مخزن Git مستقل نبوده است؛ دربارهٔ وضعیت Git در والدها یا منشأ فایل‌ها نتیجهٔ بیشتری نمی‌گیریم.

## ۵. یافته‌های بررسی Test Execution

### ۵.۱. `core/test_execution.py`

کلاس `TestExecutionService`:

- رجیستری پروفایل، Executor و محدودیت‌های اجرا را دریافت می‌کند.
- نوع ورودی‌ها را بررسی می‌کند.
- پروفایل را از رجیستری می‌گیرد.
- `ExecutionRequest` می‌سازد و آن را به `executor.execute(request)` تحویل می‌دهد.

این سرویس هماهنگ‌کننده است؛ خودش اجرای فرمان یا پیاده‌سازی محدودیت‌های سیستم‌عامل را انجام نمی‌دهد.

### ۵.۲. `core/test_executor.py`

این فایل قراردادها و مدل‌های داده را تعریف می‌کند:

- `ExecutionLimits`
- `ExecutionRequest`
- `ExecutionResult`
- `TestExecutionError`
- `TestExecutor` به‌صورت `Protocol`

در نتیجه، تعریف `TestExecutor` در این فایل به‌تنهایی یک Executor عملیاتی نیست. محدودیت‌های timeout، حافظه و CPU در قرارداد داده تعریف شده‌اند؛ اما اعمال واقعی آن‌ها باید در پیاده‌سازی اجرایی اثبات شود.

### ۵.۳. `core/test_profiles.py`

- پروفایل‌ها دارای شناسه، نام، فرمان، پوشهٔ کاری نسبی و timeout هستند.
- فرمان به شکل tuple از آرگومان‌ها تعریف می‌شود، نه یک رشتهٔ shell.
- پروفایل پیش‌فرض از `python -m pytest -q` استفاده می‌کند.
- رجیستری امکان ثبت پروفایل و بازیابی آن را دارد.

استفاده از آرایهٔ آرگومان‌ها در صورت اجرای نهایی با `shell=False` می‌تواند مناسب‌تر از shell string باشد؛ اما این فایل به‌تنهایی نحوهٔ اجرای واقعی را اثبات نمی‌کند. همچنین کنترل امن مسیر `working_directory` در برابر symlink باید در Executor بررسی شود. سطح دسترسی عامل به ثبت یا تغییر پروفایل‌ها نیز هنوز روشن نیست.

### ۵.۴. جست‌وجوی پیاده‌سازی اجرایی

جست‌وجوی زیر در `runner/core` انجام شد:

```bash
grep -R -n -E "class .*Executor|def execute|docker run|subprocess.run|Popen" ~/ilan-lab/runner/core --include="*.py"
```

خروجی فقط این موارد را نشان داد:

- تعریف `TestExecutor(Protocol)` در `core/test_executor.py`
- متد `execute` در همان قرارداد
- متد `execute` در `core/test_execution.py`

هیچ پیاده‌سازی concrete از Executor و هیچ فراخوانی آشکار `docker run`، `subprocess.run` یا `Popen` در فایل‌های Python زیر `runner/core` پیدا نشد.

**حد نتیجه‌گیری:** این جست‌وجو در `core` انجام شده بود، نه تمام مخزن؛ بنابراین برای نتیجه‌گیری قطعی دربارهٔ کل Runner باید `main.py` و سایر مسیرها نیز بررسی شوند.

## ۶. یافته‌های بررسی Bootstrap

### ۶.۱. `core/authorization.py`

کلاس `AuthorizationManager`:

- یک `approval_callback` دریافت می‌کند.
- عملیات را به‌صورت رشته دریافت می‌کند.
- فقط در صورت بازگشت دقیق `True` از callback ادامه می‌دهد.
- سپس `sudo -v` را با timeout اجرا می‌کند تا اعتبارنامهٔ sudo را بررسی/تازه‌سازی کند.

این کلاس به‌تنهایی یک موتور سیاست مجوزدهی کامل نیست:

- معنای عملیات و پارامترهای واقعی آن را ساختاریافته اعتبارسنجی نمی‌کند.
- از روی این فایل مشخص نیست تأیید به همان فراخوانی اجرایی مشخص و تغییرناپذیر متصل می‌شود.
- `sudo -v` صرفاً اعتبار sudo را تازه‌سازی/اعتبارسنجی می‌کند و به‌تنهایی اجرای بعدی را محدود یا امن نمی‌سازد.

اثر دقیق تازه‌سازی اعتبار sudo به تنظیمات sudoers، timestamp و مدل پردازه‌ها بستگی دارد و باید جداگانه ارزیابی شود.

### ۶.۲. `tools/dispatcher.py`

`ToolDispatcher.execute`:

- ابزار را از Registry می‌گیرد.
- رشتهٔ JSON را به دیکشنری تبدیل می‌کند.
- نوع آرگومان‌ها را بررسی می‌کند.
- مستقیماً `tool["execute"](arguments)` را فراخوانی می‌کند.
- در پایان، خروجی dataclass یا Path را تا حدی تبدیل می‌کند.
در همین فایل، کنترل صریح مجوز، تأیید کاربر، چرخهٔ Operation، ثبت Trace یا اعتبارسنجی schema ابزار دیده نشد. با این حال، ممکن است بخشی از این کنترل‌ها در Registry، wrapper ابزار یا لایهٔ فراخواننده قرار داشته باشد؛ برای داوری دربارهٔ کل Bootstrap باید زنجیرهٔ فراخوانی بررسی شود.
## ۷. جمع‌بندی معماری موقت

فرضیهٔ کاری مناسب برای ادامهٔ بررسی:

- Runner نامزد هستهٔ اجرایی و امنیتی است.
- Bootstrap نامزد لایهٔ عامل هوشمند و اتصال مدل است.
- میزکار (`ilan-workbench`) باید محدودهٔ کاری و محل تبادل مأموریت/گزارش باشد.
- اتصال عامل به Runner باید از یک رابط محدود و قابل ممیزی عبور کند؛ نه از دسترسی مستقیم و نامحدود به internals یا ترمینال میزبان.

این هنوز **تصمیم نهایی معماری نیست**. ابتدا باید اتصال واقعی اجزای Runner و مسیر اجرای ابزارها اثبات شود.

هدف پاسخ به این پرسش است:

**آیا درخواست واقعی از کنترل مجوز عبور می‌کند، به Operation تبدیل می‌شود، اجرا می‌شود و نتیجهٔ واقعی آن در Trace ثبت می‌شود؟**

پس از آن باید پیاده‌سازی‌های Registry و ابزارهای Bootstrap نیز بررسی شوند تا مرز مسئولیت‌ها و نقاط اتصال مشخص شوند.

## ۹. محدودیت‌های این یادداشت

- این الحاقیه بر اساس خروجی‌ها و کدهایی است که تا این مرحله در گفتگو بررسی شده‌اند.- هنوز آزمون کامل و تازه‌ای از کل Runner اجرا نشده است.
- نتیجهٔ جست‌وجوی محدود به `runner/core` را نباید به کل مخزن تعمیم داد.
- هیچ تغییری در کدها، تنظیمات سیستم، مجوزهای Docker یا Git در این مرحله درخواست یا انجام نشده است.
- این فایل فقط پیش‌نویس الحاق به نسخهٔ بعدی سند اصلی است؛ وضعیت Library را تغییر نمی‌دهد.

## ۱۰. تغییر اولویت پروژه: راه‌اندازی سریع ابزارهای کاری ایلان

**تصمیم جدید کاربر:** اولویت فوری پروژه، راه‌اندازی هرچه سریع‌تر ابزارهای کاربردی ایلان است تا او بتواند در ادامهٔ جابه‌جایی و توسعهٔ محیط، بازوی اجرایی مؤثری باشد. طراحی و پیاده‌سازی امنیت حداکثری به مرحلهٔ بعد منتقل می‌شود.

این تغییر به معنی کنار گذاشتن کامل کنترل‌های پایه نیست؛ فقط به این معنی است که در نسخهٔ اولیه، از پیچیده‌سازی زودهنگام معماری امنیتی پرهیز می‌کنیم و ابتدا چرخهٔ کاری واقعی را فعال می‌سازیم.

### ۱۰.۱. تقسیم مسئولیت قطعی در گردش کار

- **کاربر:** تصمیم‌گیر نهایی، تعیین‌کنندهٔ هدف‌ها و تأییدکنندهٔ تصمیم‌های مهم.
- **ایگور (ChatGPT):** مسئول تحلیل، طراحی راه‌حل، بررسی کد، نوشتن یا اصلاح کد و دستورات دقیق، تعیین ترتیب اجرا، تعریف تست‌ها و ارزیابی مستقل نتایج. ایگور باید دستور و کد اجرایی را به ایلان بدهد.
- **ایلان:** بازوی اجرایی ایگور؛ مأموریت و کد/دستور مشخص را دریافت می‌کند، آن را در محدودهٔ مجاز اجرا می‌کند و نتیجهٔ واقعی، خطاها و شواهد اجرا را گزارش می‌دهد.

ایلان در این مرحله مرجع مستقل تعیین معماری یا تغییر هدف مأموریت نیست. او می‌تواند ایراد یا پیشنهاد را گزارش کند، اما تغییر مسیر، گسترش دامنهٔ مأموریت یا اجرای اقدام اضافی نیازمند دستور جدید ایگور و در موارد تصمیم‌گیری، تأیید کاربر است.

### ۱۰.۲. اصل اجرای مأموریت

1. ایگور ابتدا هدف، فایل‌های هدف، تغییر مورد انتظار و معیار پذیرش را مشخص می‌کند.
2. ایگور دستورالعمل و کد لازم را به‌صورت صریح و قابل اجرا در اختیار ایلان می‌گذارد.
3. ایلان فقط همان مأموریت را اجرا می‌کند؛ نباید دستور را به ابتکار خود بازنویسی یا دامنهٔ آن را گسترش دهد.
4. ایلان خروجی واقعی را همراه با مسیر فایل‌های تغییرکرده، خلاصهٔ تغییر، نتیجهٔ تست و متن خطاهای احتمالی بازمی‌گرداند.
5. ایگور نتیجه را بررسی می‌کند و در صورت نیاز مأموریت بعدی را صادر می‌کند.
6. تصمیم نهایی دربارهٔ تغییرات مهم و جهت پروژه با کاربر است.

### ۱۰.۳. اولویت فوری ابزارها: MVP کاربردی

هدف نخست، فعال‌کردن یک چرخهٔ ساده و قابل اتکاست: «شناخت فایل‌ها ← خواندن ← تغییر ← مشاهدهٔ diff ← تست ← گزارش».

ابزارهای اولویت‌دار:

| ابزار | وضعیت/اولویت | کاربرد |
|---|---|---|
| `list_files` | موجود؛ اصلاح فوری | فهرست‌کردن فایل‌ها و پوشه‌های Workspace |
| `read_file` | موجود؛ اصلاح فوری | خواندن کامل یا بازه‌ای فایل |
| `apply_patch` | موجود؛ اصلاح فوری | اعمال تغییرات مشخص و محدود |
| `run_tests` | موجود؛ اصلاح/اتصال فوری | اجرای تست‌های پروژه |
| `search_files` | جدید؛ اولویت بالا | یافتن فایل بر اساس نام یا الگو |
| `search_text` | جدید؛ اولویت بالا | جست‌وجوی متن و نمادها در فایل‌ها |
| `write_file` | جدید؛ اولویت بالا | ایجاد یا جایگزینی محتوای فایل مشخص |
| `get_diff` | جدید؛ اولویت بالا | نمایش دقیق تغییرات قبل/بعد |

ابزارهای تکمیلی پس از فعال‌شدن MVP:
- `get_file_info`
- `create_directory`
- `get_test_results`
- `get_execution_log`
- `read_task`
- `write_report`
- `update_task_status`
- `request_approval`

### ۱۰.۴. ترتیب اجرای سریع

**گام A — تثبیت ابزارهای موجود**
- بررسی و رفع اشکال `list_files` و `read_file`.
- حل ناسازگاری مسیر Workspace بین Bootstrap، Workbench و ابزارها.
- بررسی و آزمایش `apply_patch` و `run_tests`.
- تعریف یک قرارداد روشن برای مسیرها: ابزارها باید بدانند مسیر نسبی نسبت به کدام ریشه تفسیر می‌شود؛ مسیرهای مبهم نباید بی‌صدا به ریشه‌های دیگر نگاشت شوند.

**گام B — تکمیل ابزارهای ضروری**
- افزودن `search_files` و `search_text`.
- افزودن `write_file` با رفتار روشن برای ایجاد/جایگزینی.
- افزودن `get_diff` برای بررسی تغییرات.
- ترجیحاً ابزارها از همان قرارداد Workspace و همان لایهٔ دسترسی فایل استفاده کنند؛ از ایجاد چند مسیر ناسازگار برای خواندن/نوشتن پرهیز شود.

**گام C — آزمون چرخهٔ واقعی**
- فهرست‌کردن فایل‌های یک پروژهٔ آزمایشی.
- خواندن یک فایل مشخص.
- اعمال یک تغییر کوچک و از پیش تعریف‌شده.
- مشاهدهٔ diff.
- اجرای تست مربوط.
- بازگرداندن گزارش دقیق به ایگور.
- تا قبل از موفقیت این چرخه، توسعهٔ قابلیت‌های خودگردان گسترده‌تر اولویت ندارد.

### ۱۰.۵. سطح کنترل در نسخهٔ سریع

کاربر تأکید کرده است که در این مقطع، سرعت راه‌اندازی بر پیاده‌سازی امنیت حداکثری اولویت دارد و کنترل‌های پایه مانع پیشرفت نیستند. بنابراین:
- در این مرحله ساخت sandbox کامل، سیاست مجوزدهی پیچیده، محدودیت دقیق منابع و ممیزی پیشرفته را پیش‌شرط MVP نمی‌کنیم.
- با این حال، محدودهٔ کاری اولیه همچنان Workspace مشخص است؛ دسترسی نامحدود به کل سیستم میزبان یا اجرای نامحدود فرمان‌ها جزو MVP نیست.

این‌ها کنترل‌های پایهٔ عملیاتی‌اند، نه ادعای تکمیل امنیت. ارزیابی و تقویت امنیت به مرحلهٔ مستقل بعدی موکول شده است.

### ۱۲.۳. نکات مثبت که باید حفظ شوند

- استفاده از Windows Credential Manager به‌جای قرار دادن توکن در سورس.
- رد کردن Backend ناامن Keyring.
- ذخیرهٔ Updateها و Offset در یک تراکنش؛ این کار از جلو رفتن Offset بدون ثبت همان Batch جلوگیری می‌کند.
- استفاده از `BEGIN IMMEDIATE` در نقاط حساس نوشتن.
- Claim اتمیک پیام ورودی با UPDATE شرطی.
- ذخیرهٔ پاسخ مدل و قطعات آن پیش از شروع ارسال به تلگرام.
- ثبت وضعیت هر قطعهٔ خروجی و امکان ادامهٔ ارسال پس از Restart.
- Retry با Backoff برای خطاهای موقت شبکه و Telegram.
- بررسی وجود Webhook پیش از شروع Long Polling.

### ۱۲.۴. تصمیم فعلی و مرز کار
**تصمیم صریح کاربر: در مرحلهٔ فعلی به Receiver دست نمی‌زنیم.**

1. هیچ اصلاح، بازنویسی، جابه‌جایی یا تغییر تنظیمی در `telegram_receiver.py` انجام نشود.
2. هیچ تغییری در دیتابیس `ilan_receiver.sqlite3` یا توکن ذخیره‌شده انجام نشود.
3. Receiver فعلاً به‌عنوان پل ارتباطی موجود حفظ شود؛ رفع ریسک‌های ثبت‌شده به مرحلهٔ جداگانه موکول است.
4. اولویت فوری، راه‌اندازی حداقلی ابزارهای کاری ایلان طبق بخش ۱۰ همین الحاقیه است.
5. مسیر MVP همچنان این است: `list_files` و `read_file`، سپس `apply_patch` و `run_tests`؛ بعد از تثبیت آن‌ها ابزارهای جست‌وجو، نوشتن و Diff تکمیل شوند.
6. اگر آزمایش ارتباط Bot به Bot نشان دهد مسیر فعلی اصولاً کار نمی‌کند، موضوع ابتدا به‌صورت یک مانع معماری گزارش شود؛ تغییر Receiver بدون تصمیم جدید کاربر انجام نشود.

### ۱۲.۵. ترتیب ادامهٔ کار

- Receiver را فعلاً کنار می‌گذاریم و کد آن را تغییر نمی‌دهیم.
- به بررسی و راه‌اندازی ابزارهای موجود Bootstrap و قرارداد مسیر Workspace بازمی‌گردیم.

- پس از موفقیت چرخهٔ حداقلی، دربارهٔ ابزارهای جدید و سخت‌سازی Receiver تصمیم می‌گیریم.

**وضعیت این بخش:** یافته‌ها ثبت شدند؛ هیچ اقدام اجرایی روی Receiver مجاز یا انجام‌شده نیست.

## ۱۳. توافق برای ادامهٔ راه‌اندازی MVP — بازرسی ابزارهای موجود

**تصمیم و توافق کاربر:** پیشنهاد مسیر ادامهٔ کار پذیرفته شد. هدف، راه‌اندازی ابزارهای موجود است؛ نه بازنویسی یا ساخت نسخه‌های تکراری.

### ۱۳.۱. اصل راهنما

چهار ابزار `list_files`، `read_file`، `apply_patch` و `run_tests` در سوابق پروژه به‌عنوان ابزارهای موجود ثبت شده‌اند. بنابراین تا وقتی بازرسی کد و تست‌ها خلاف آن را نشان نداده، باید آن‌ها را دارایی موجود پروژه فرض کنیم و ابتدا علت اختلال یا اتصال ناقص را پیدا کنیم.

وجود فایل پیاده‌سازی یا تست، به‌تنهایی اثبات نمی‌کند ابزار در مسیر واقعی مکالمهٔ ایلان قابل فراخوانی است. همچنین موفقیت تست واحد، معادل موفقیت زنجیرهٔ انتها‌به‌انتها نیست.

### ۱۳.۲. مسیر اجرایی مورد توافق

1. مبنای بررسی، سند اصلی پروژه در نسخهٔ ۰.۳ و همین الحاقیهٔ موقت خواهد بود.
2. فایل‌های واقعی پیاده‌سازی و تست چهار ابزار موجود بررسی می‌شوند؛ ابزارها از صفر بازنویسی یا دوباره‌سازی نمی‌شوند.
3. قرارداد مسیر Workspace با مسیر واقعی اجرای ایلان و محل واقعی فایل‌های پروژه تطبیق داده می‌شود.4. هر چهار ابزار از مسیر واقعی ارتباطی ایلان آزمایش می‌شوند، نه فقط با تست‌های واحد.
5. پس از موفقیت آزمون‌ها، یک مأموریت کوچک و محدود واقعی به ایلان داده می‌شود و نتیجه، فایل‌های تغییرکرده، diff و تست‌ها مستقلاً توسط ایگور بررسی می‌شوند.

### ۱۳.۳. زنجیره‌ای که باید اثبات شود

برای هر ابزار، مسیر کامل زیر باید بررسی شود:

`ثبت ابزار ← ساخت/تبدیل درخواست مدل ← تشخیص فراخوانی ابزار ← Dispatcher ← اجرای تابع ابزار ← دسترسی به Workspace ← بازگرداندن نتیجه به مکالمه`

باید مشخص شود اختلال احتمالی در کدام حلقه رخ می‌دهد. بررسی صرف تابع ابزار یا تست واحد برای اعلام آمادگی عملیاتی کافی نیست.

### ۱۳.۴. ترتیب بازرسی

- شناسایی مسیر و نسخهٔ واقعی `ilan-bootstrap` که عامل در حال اجرا از آن استفاده می‌کند.
- یافتن فایل‌های ثبت ابزار، Registry، Dispatcher و پیاده‌سازی چهار ابزار.
- یافتن تست‌های مرتبط و اجرای آن‌ها بدون تغییر کد.
- استخراج مقدار واقعی Workspace root و مقایسهٔ آن با مسیرهای مورد استفادهٔ ابزارها.
- بررسی گزارش خطا و یک اجرای واقعی کنترل‌شده از هر ابزار.
- ثبت علت ریشه‌ای و سپس صدور مأموریت اصلاحی کوچک و مشخص، فقط در صورت اثبات نیاز.

### ۱۳.۵. محدودیت تغییرات

- تا پیش از بازرسی، هیچ ابزار جدیدی اضافه نمی‌شود.
- هیچ پیاده‌سازی موجودی صرفاً به دلیل خطای فراخوانی بازنویسی نمی‌شود.
- تغییرات فقط پس از تشخیص علت و با مأموریت محدود انجام می‌شوند.
- Receiver تلگرام، دیتابیس و توکن آن همچنان خارج از دامنهٔ این کار هستند و باید دست‌نخورده بمانند.
- اختیار تصمیم نهایی و تأیید تغییرات مهم با کاربر است.

**وضعیت:** مسیر ادامه مورد توافق است؛ بازرسی فنی این مرحله هنوز انجام نشده و نباید آن را انجام‌شده تلقی کرد.

- **OpenRouter:** وابستگی مدل اصلی Ilan نیست؛ استفادهٔ قبلی آن مربوط به پروژهٔ Saloon است. نباید OpenRouter را به مسیر اصلی Ilan منتقل یا به‌عنوان پیش‌نیاز اتصال ابزارهای Ilan در نظر گرفت.
- **ابزارها:** چهار ابزار موجود در Bootstrap یعنی `list_files`، `read_file`، `apply_patch` و `run_tests` باید برای استفاده از مدل محلی و قابل فراخوانی شدن در مکالمهٔ Telegram تطبیق و متصل شوند. هدف، استفاده از دارایی‌های موجود است، نه ساخت چهار ابزار موازی یا بازنویسی بی‌دلیل آن‌ها.

نمای مفهومی مسیر هدف:

`Telegram → Receiver فعلی → ask_model(prompt) → Ollama/GPT-OSS Tool-Calling Loop → Tool Registry → Tool Dispatcher → ابزارهای موجود → نتیجه به مدل → پاسخ متنی به Receiver → Telegram`

این نمودار معماری هدف را نشان می‌دهد؛ اتصال واقعی هیچ‌یک از حلقه‌ها تا زمان آزمون انتها‌به‌انتها، اثبات‌شده تلقی نمی‌شود.

### ۱۴.۲. ترتیب اجرایی مورد توافق

1. بررسی نسخهٔ واقعی `ollama_client.py` و تنظیمات مدل محلی، از جمله مدل انتخاب‌شده و شیوهٔ فعلی فراخوانی Ollama.

### ۱۵.۱. فایل بررسی‌شده و تنظیمات گزارش‌شده

### ۱۵.۲. رفتار فعلی Client

کد فعلی:

## ۱۶. بررسی سه فایل AgentLoop، ToolRegistry، ToolDispatcher و تطبیق با Ollama Client

**وضعیت: نسخه‌های محلی هر چهار فایل در گفتگو از سوی کاربر ارائه و بررسی شدند؛ ثبت در ۲۰۲۶-۱۱-۲۰.**

این بخش، ادامه و تکمیل بررسی بخش ۱۵ است. محتوای فایل‌ها بر اساس نسخه‌هایی است که کاربر در گفتگو ارائه کرده؛ هنوز Hash یا محتوای آن‌ها با فایل‌های روی دیسک محیط در حال اجرا تطبیق داده نشده است.

### ۱۶.۱. فایل‌های دریافت‌شده

- `agent/loop.py`
- `tools/registry.py`
- `tools/dispatcher.py`
- `ollama_client.py`

نسخهٔ ارائه‌شدهٔ `agent/loop.py` از نظر ساختار کلی با نسخه‌ای که پیش‌تر از شاخهٔ `main` مخزن GitHub مشاهده شده بود هم‌راستاست؛ نسخهٔ محلی Logging جزئی‌تری دارد. این تطبیق، اثبات نمی‌کند فایل محلی در حال اجرا همان نسخهٔ GitHub است.

### ۱۶.۲. یافته‌های AgentLoop

کلاس `AgentLoop`:

- به شیئی با متد `chat(messages, tools=tools)` نیاز دارد.
- پاسخ مدل را با ساختار `response["choices"][0]["message"]` می‌خواند.
- فراخوانی ابزارها را از `assistant_message["tool_calls"]` استخراج می‌کند.
- برای تعریف ابزارها از `tool_registry.definitions()` استفاده می‌کند.
- اجرای هر فراخوانی را به `tool_dispatcher.execute(name, arguments)` می‌سپارد.
- نتیجه را با نقش `tool` و شناسهٔ `tool_call_id` به تاریخچه اضافه می‌کند تا در فراخوانی بعدی به مدل برگردد.
- خطای اجرای هر ابزار را به‌صورت نتیجهٔ ناموفق به تاریخچهٔ مکالمه اضافه می‌کند؛ خطای فراخوانی مدل را ثبت و دوباره پرتاب می‌کند.
- مقدار `finish_reason` را فقط در Log ثبت می‌کند و بر اساس آن تصمیم کنترلی نمی‌گیرد.
- مقدار پیش‌فرض `max_tool_rounds=2` دارد؛ در این حالت حداکثر دو دور Tool Call و یک فراخوانی نهایی مدل در نظر گرفته می‌شود. تعداد ابزارهای اجراشده می‌تواند از دو بیشتر باشد، چون هر دور ممکن است چند Tool Call داشته باشد.

نکتهٔ پیاده‌سازی: AgentLoop آرگومان‌های Tool Call را برای استخراج مسیر و Logging به‌صورت محلی Parse می‌کند، اما رشتهٔ اصلی `arguments` را به Dispatcher می‌فرستد. این Parse اولیه در اجرای ابزار نقشی ندارد؛ Dispatcher خودش رشته را Parse می‌کند.

### ۱۶.۳. یافته‌های ToolRegistry

کلاس `ToolRegistry`:

- ابزارها را با فیلدهای `name`، `description`، `parameters` و `execute` نگهداری می‌کند.
- از ثبت دوبارهٔ نام یکسان جلوگیری می‌کند.
- متد `get(name)` رکورد ابزار ثبت‌شده را برمی‌گرداند.
- متد `definitions()` فقط `name`، `description` و `parameters` را در قالب Function Tool به مدل معرفی می‌کند و تابع اجرایی را در تعریف ارسالی به مدل قرار نمی‌دهد.

در ساختار فعلی، Registry و AgentLoop از نظر نام متد `definitions()` و قالب تعریف ابزار با یکدیگر سازگارند.

### ۱۶.۴. یافته‌های ToolDispatcher

کلاس `ToolDispatcher`:

- ابزار را از طریق `registry.get(name)` پیدا می‌کند.
- اگر آرگومان‌ها رشته باشند، آن‌ها را با `json.loads` تبدیل می‌کند.- الزام می‌کند آرگومان نهایی یک دیکشنری باشد.
- تابع اجرایی ثبت‌شده را با یک آرگومان دیکشنری فراخوانی می‌کند: `tool["execute"](arguments)`.
- خروجی dataclass را با `asdict` و خروجی `Path` را به رشته تبدیل می‌کند.
قرارداد Registry و Dispatcher با یکدیگر سازگار است. نام ابزار ناشناخته در Registry به `KeyError` منجر می‌شود؛ در مسیر فعلی AgentLoop این خطا در سطح اجرای Tool گرفته و به‌صورت نتیجهٔ ناموفق به مدل برگردانده می‌شود.
اعتبارسنجی schema آرگومان‌ها در Dispatcher دیده نمی‌شود؛ بررسی آن باید با تعریف ابزارها و wrapperهای اجرایی واقعی انجام شود. تبدیل خروجی نیز فعلاً فقط dataclass و `Path` را پوشش می‌دهد و دربارهٔ سایر انواع خروجی باید قرارداد ابزارها بررسی شود.

### ۱۶.۵. ناسازگاری قطعی Ollama Client فعلی با AgentLoop

در `ollama_client.py` ارائه‌شده:

- فقط تابع `ask_model(prompt)` تعریف شده و متد `chat(messages, tools=tools)` وجود ندارد.
- ورودی فقط یک prompt متنی است؛ تاریخچهٔ پیام‌ها به شکل فهرست نقش‌دار دریافت نمی‌شود.
- در payload فعلی فیلد `tools` ارسال نمی‌شود.
- پاسخ فقط از `result["message"]["content"]` استخراج می‌شود؛ `message.tool_calls` پردازش نمی‌شود.
- تابع در پایان یک رشته برمی‌گرداند.

در مقابل، AgentLoop به متد `chat(messages, tools=tools)` و پاسخ ساختاریافته با مسیر `choices[0].message` نیاز دارد. بنابراین این دو جزء در وضعیت فعلی مستقیماً قابل اتصال نیستند.

علاوه بر تفاوت امضای متد، قالب پاسخ بومی `/api/chat` در Ollama با قالب `choices` مورد انتظار AgentLoop یکسان نیست. هر آداپتر یا Client جدید باید پاسخ Ollama را به قرارداد مورد انتظار AgentLoop تبدیل کند، یا قرارداد AgentLoop را با تصمیم معماری روشن تغییر دهد؛ این انتخاب هنوز نهایی نشده است.

### ۱۶.۶. نتیجهٔ معماری و مسیر پیشنهادی

- سه جزء AgentLoop، ToolRegistry و ToolDispatcher از نظر قراردادهای اصلی با یکدیگر سازگارند و در کد ارائه‌شده دلیلی برای بازنویسی آن‌ها دیده نشد.
- گسست اثبات‌شده در سطح کدهای ارائه‌شده، بین Ollama Client فعلی و AgentLoop است.
- مسیر کم‌تغییر پیشنهادی، افزودن قابلیت Client سازگار با `chat(messages, tools)` و تطبیق پاسخ Ollama با قالب مورد انتظار AgentLoop است.
- قرارداد موجود `ask_model(prompt) -> str` تا زمان بررسی محل استفاده و وابستگی‌های Receiver حفظ شود؛ می‌توان قابلیت جدید را در کنار آن طراحی کرد، نه اینکه بی‌دلیل تابع فعلی حذف یا تغییر داده شود.
- پیش از انتخاب محل نهایی آداپتر، باید محل ساخت AgentLoop و Client، و محل فراخوانی فعلی `ask_model` در مسیر واقعی Receiver بررسی شود.

### ۱۶.۷. نکات جانبی Client که در بررسی ثبت شدند

- `OLLAMA_TIMEOUT = 2000` در `urllib.request.urlopen` برحسب ثانیه تفسیر می‌شود، نه میلی‌ثانیه؛ یعنی حداکثر حدود ۳۳ دقیقه و ۲۰ ثانیه.
- کد صریحاً `HTTPError` را مدیریت می‌کند؛ خطاهایی مانند `URLError` در این تابع به‌صورت اختصاصی مدیریت نشده‌اند و به فراخواننده منتقل می‌شوند.- در `THINKING_MODE="auto"`، برای مدل تنظیم‌شدهٔ GPT-OSS مقدار صریح `think` به payload افزوده نمی‌شود؛ رفتار پیش‌فرض Ollama/مدل باید در آزمایش واقعی مشخص شود.
- `finish_reason` در AgentLoop فقط ثبت می‌شود؛ رفتار پاسخ‌های ناقص یا پایان با علت‌هایی مانند محدودیت طول هنوز آزمایش نشده است.

این موارد یافته‌های بررسی کد هستند و به‌تنهایی به معنی وجود خطای زمان اجرا یا نیاز قطعی به اصلاح همهٔ آن‌ها نیستند.
### ۱۶.۸. وضعیت و گام بعدی

فایل بعدی موردنیاز برای ادامهٔ بررسی، نسخهٔ محلی `telegram_receiver.py` است؛ به‌ویژه بخش‌هایی که `ask_model` را فراخوانی می‌کنند و هرگونه ساخت یا اتصال Client، AgentLoop، Registry و Dispatcher در آن‌ها انجام می‌شود.

هدف، تعیین محل اتصال بدون تغییر Receiver است. اگر اتصال از لایهٔ مدل/آداپتر ممکن باشد، همان مسیر بر تغییر Receiver ترجیح دارد. هر ضرورت فنی برای تغییر Receiver باید پیش از اقدام گزارش شود و نیازمند تصمیم تازهٔ کاربر است.

**محدودیت وضعیت:** دریافت و بررسی کدها در گفتگو انجام شده است؛ اما هیچ‌یک از فایل‌ها تغییر نکرده‌اند، هیچ تستی اجرا نشده، هیچ Tool Call واقعی از Telegram انجام نشده و اتصال انتها‌به‌انتها هنوز اثبات نشده است. تا پیش از روشن‌شدن و آزمایش مسیر واقعی، مأموریت اجرایی تازه‌ای برای Ilan ارسال نشود.

**یادداشت اصلاح وضعیت بخش ۱۵:** فهرست سه فایل درخواستی بخش ۱۵.۴ اکنون از کاربر دریافت و بررسی شده است؛ بنابراین وضعیت «در انتظار دریافت» در آن بخش با این بخش ۱۶ تکمیل می‌شود. سایر محدودیت‌های اجرایی بخش ۱۵.۵ همچنان برقرارند.

## ۱۷. بررسی Telegram Receiver و تعیین مسیر واقعی اجرای مدل

**وضعیت: کد کامل `telegram_receiver.py` در گفتگو از سوی کاربر ارائه و بررسی شد؛ ۲۰۲۶-۱۱-۲۰.**

این بررسی بر اساس متن فایل ارائه‌شده است. هنوز Hash یا نسخهٔ روی دیسک محیط در حال اجرا مستقلاً تطبیق داده نشده است.

### ۱۷.۱. یافتهٔ قطعی دربارهٔ مسیر فعلی فراخوانی مدل

در ابتدای Receiver فقط این اتصال مدل وارد شده است:

```python
from ollama_client import ask_model
```

در تابع `process_one_incoming_message()` نیز فراخوانی واقعی چنین است:

```python
answer = ask_model(row["message_text"])
```

در فایل ارائه‌شده هیچ import، ساخت نمونه یا فراخوانی‌ای از موارد زیر دیده نمی‌شود:

- `AgentLoop`
- `ToolRegistry`
- `ToolDispatcher`

بنابراین مسیر فعلی درخواست‌های Telegram از AgentLoop عبور نمی‌کند. Receiver متن پیام ذخیره‌شده را مستقیماً به `ask_model` می‌دهد و یک رشتهٔ پاسخ دریافت می‌کند. در نتیجه، وجود سه فایل AgentLoop/Registry/Dispatcher به‌تنهایی به معنای فعال‌بودن Tool Calling در مسیر واقعی Ilan نیست.

**مسیر فعلی مشاهده‌شده:**

`Telegram polling → save_updates_and_offset → SQLite incoming_messages → process_one_incoming_message → ask_model(message_text) → Ollama text response → SQLite outgoing_chunks → Telegram sendMessage`

### ۱۷.۲. پیامد برای طراحی اتصال

- محل فعلی اتصال مدل به Receiver، تابع `ask_model` در `ollama_client.py` است.
- AgentLoop هنوز در زنجیرهٔ اجرای Receiver وارد نشده است.
- صرفاً افزودن متد `chat(messages, tools)` به Client کافی نیست؛ باید یک نقطهٔ مشخص، AgentLoop را با Registry و Dispatcher موجود بسازد و درخواست را از آن عبور دهد.
- برای پرهیز از تغییر غیرضروری Receiver، ابتدا باید بررسی شود آیا می‌توان در لایهٔ مدل/تابع ورودی فعلی، یک adapter یا تابع سازگار اضافه کرد و قرارداد `ask_model(prompt) -> str` را حفظ کرد.
- اگر برای عبور درخواست از AgentLoop ناگزیر به تغییر محل فراخوانی در Receiver باشیم، این نیاز باید با diff محدود و دلیل فنی روشن مطرح شود؛ تغییر Receiver خودکار یا از پیش مجاز فرض نشود.

### ۱۷.۳. ویژگی‌های فعلی Receiver که باید حفظ شوند

Receiver علاوه بر فراخوانی مدل، مسئولیت‌های عملیاتی مهمی دارد که در اتصال جدید نباید ناخواسته مختل شوند:

- دریافت Telegram updates و فیلترکردن پیام‌ها بر اساس `TARGET_CHAT` و `TARGET_BOT_ID`.
- ذخیرهٔ پیام‌های ورودی و offset در SQLite.
- مدیریت وضعیت پیام‌ها و بازیابی پیام‌هایی که هنگام پردازش قطع شده‌اند.
- ذخیرهٔ پاسخ مدل و قطعه‌های خروجی در SQLite پیش از ارسال به Telegram.
- تقسیم پاسخ‌های طولانی و پیگیری وضعیت ارسال هر قطعه.
- تلاش مجدد برای خطاهای موقت شبکه و Telegram.
- نگهداری توکن با Windows Credential Manager و پرهیز از چاپ URL حاوی توکن.
- جلوگیری از polling هم‌زمان در صورت فعال‌بودن webhook.

این مسئولیت‌ها خارج از دامنهٔ اصلاح اتصال Tool Calling هستند و باید دست‌نخورده بمانند، مگر اینکه دلیل فنی مشخص و تأیید جداگانه وجود داشته باشد.

### ۱۷.۴. محدودیت زمینهٔ مکالمه در مسیر فعلی
در مسیر فعلی، هر بار فقط `row["message_text"]` به `ask_model` داده می‌شود. هرچند پیام‌های ورودی در SQLite ذخیره می‌شوند، در کد پردازش مشاهده‌شده تاریخچهٔ پیام‌های قبلی برای مدل بازیابی و ارسال نمی‌شود. بنابراین نباید فرض کرد مدل در هر درخواست زمینهٔ مکالمات قبلی Telegram را دریافت می‌کند.
AgentLoop نیز در هر اجرای `run(user_message)` یک فهرست پیام تازه شامل system prompt و همان user message می‌سازد؛ تاریخچهٔ پایدار میان درخواست‌ها در کد ارائه‌شده دیده نمی‌شود. مدیریت حافظه/تاریخچه موضوعی جدا از فعال‌سازی Tool Calling است و نباید بدون تصمیم معماری با این مرحله ادغام شود.

### ۱۷.۵. نتیجه و وضعیت بعدی

1. گسست اتصال اکنون در سطح Receiver نیز تأیید شد: مسیر واقعی Telegram مستقیماً `ask_model` را صدا می‌زند و AgentLoop را دور می‌زند.
2. سه فایل AgentLoop، Registry و Dispatcher همچنان از نظر قراردادهای داخلی قابل حفظ به نظر می‌رسند؛ نیاز به اصلاح آن‌ها باید فقط با شواهد آزمون یا ناسازگاری مشخص اثبات شود.
3. گام طراحی بعدی، تعیین کم‌تغییرترین نقطهٔ ورود AgentLoop در مسیر فعلی است؛ سپس باید Client سازگار با Ollama Tool Calling و adapter خروجی طراحی شود.
4. پیش از هر تغییر، باید محل ثبت/ساخت ابزارهای واقعی چهارگانه و مسیر Workspace آن‌ها نیز بررسی شود تا Dispatcher به همان ابزارها و همان محدودهٔ مجاز متصل شود.
5. هیچ فایل اجرایی تغییر نکرده، هیچ تستی اجرا نشده و هیچ فراخوانی Tool از Telegram واقعی اثبات نشده است. توکن، دیتابیس و Receiver نباید در مأموریت اصلاح Client/AgentLoop دستکاری شوند مگر با تصمیم و مجوز مستقل کاربر.
6. تا قبل از تکمیل طراحی و ارائهٔ دستور مشخص، هیچ مأموریت اجرایی تازه‌ای برای Ilan ارسال نشود.

**یادداشت اصلاح بخش ۱۶.۸:** فایل `telegram_receiver.py` اکنون دریافت و بررسی شده است؛ بنابراین گام «دریافت Receiver» تکمیل شده و نتیجهٔ آن در این بخش ۱۷ ثبت شده است.

## ۱۹. اثبات عملی Tool Calling در Ollama و بررسی نسخهٔ فعلی Client
**وضعیت: کد کامل `ollama_client.py` از سوی کاربر ارائه و آزمایش مستقیم Tool Calling در PowerShell موفق شد؛ ۲۰۲۶-۱۱-۲۰.**

### ۱۹.۱. کد فعلی `ollama_client.py` — یافته‌های قطعی

نسخهٔ ارائه‌شده شامل تابع `ask_model(prompt)` است که:

- مدل را از `MODEL_NAME` و حالت تفکر را از `THINKING_MODE` می‌گیرد.
- فقط یک پیام با نقش `user` و محتوای `prompt` به `/api/chat` می‌فرستد.
- مقدار `stream` را `False` قرار می‌دهد.
- در حالت‌های `on` و `off` مقدار `think` را صریحاً تنظیم می‌کند؛ در حالت `auto` برای مدل GPT-OSS مقدار صریحی نمی‌فرستد.
- پاسخ را فقط از `result["message"]["content"]` استخراج و به شکل رشته برمی‌گرداند.
- فقط `HTTPError` را به `RuntimeError` تبدیل می‌کند؛ خطاهای ارتباطی دیگر مانند `URLError` در این تابع به‌طور اختصاصی مدیریت نشده‌اند.
- مقدار `OLLAMA_TIMEOUT = 2000` را به `urlopen` می‌دهد؛ واحد timeout در این API ثانیه است، نه میلی‌ثانیه.

در این نسخه، فیلد `tools` به درخواست افزوده نمی‌شود، تاریخچهٔ پیام‌های نقش‌دار دریافت نمی‌شود و `message.tool_calls` پردازش نمی‌شود. بنابراین این تابع به‌تنهایی Client موردنیاز AgentLoop نیست.

**نکتهٔ رفتاری مهم:** اگر Ollama در پاسخ یک Tool Call با `content` خالی برگرداند، `ask_model` فعلی صرفاً رشتهٔ خالی برمی‌گرداند و اطلاعات Tool Call را از دست می‌دهد. پس نباید AgentLoop را از مسیر این تابع عبور داد؛ قابلیت جدید باید جداگانه اضافه شود و قرارداد فعلی `ask_model(prompt) -> str` حفظ شود.

### ۱۹.۲. آزمایش مستقیم Tool Calling

کاربر درخواست مستقیمی به endpoint زیر فرستاد:

`POST http://localhost:11434/api/chat`

در درخواست:

- مدل: `gpt-oss-20b-local:latest`
- ابزار تعریف‌شده: `demo_lookup`
- شرح ابزار: ابزار آزمایشی بی‌خطر و بدون اقدام واقعی
- پارامتر اجباری: `query` از نوع رشته
- مقدار مورد انتظار: `ilan-tool-test`
- `stream = false`

خروجی واقعی PowerShell:

```text
Role:
assistant

Content:

Tool Calls:
{
    "id": "IOCuASNI8KBnfYKTyCpSHXNhhvt5jE53",
    "function": {
        "index": 0,
        "name": "demo_lookup",
        "arguments": {
            "query": "ilan-tool-test"
        }
    }
}

Done:
True

Done Reason:
stop
```

### ۱۹.۳. نتیجهٔ اثبات‌شده

این آزمایش نشان می‌دهد:

1. درخواست دارای تعریف Function Tool توسط Ollama پذیرفته شد.
2. مدل پاسخ دستیار را به‌صورت Tool Call تولید کرد، نه پاسخ متنی معمول.
3. پاسخ بومی Ollama شامل `message.tool_calls` بود.
4. نام ابزار دقیقاً `demo_lookup` و مقدار آرگومان دقیقاً `ilan-tool-test` بود.
5. پاسخ با `done = true` و `done_reason = stop` پایان یافت.

بنابراین **تولید و بازگرداندن Tool Call در مدل محلی و نسخهٔ فعلی Ollama به‌صورت عملی اثبات شد.**

### ۱۹.۴. مرز اثبات و مواردی که هنوز آزمایش نشده‌اند

این تست فقط تولید Tool Call و ساختار پاسخ Ollama را بررسی کرد. هیچ تابعی برای `demo_lookup` ثبت یا اجرا نشد و هیچ نتیجه‌ای به مدل بازگردانده نشد. در نتیجه موارد زیر هنوز اثبات نشده‌اند:

- تبدیل پاسخ بومی Ollama به قالب مورد انتظار AgentLoop؛
- سازگاری دقیق شناسهٔ Tool Call و نوع آرگومان‌ها با AgentLoop و Dispatcher؛
- اجرای واقعی ابزار توسط Dispatcher؛
- افزودن پاسخ ابزار با نقش `tool` و شناسهٔ متناظر به تاریخچه؛
- دریافت پاسخ نهایی مدل پس از مشاهدهٔ نتیجهٔ ابزار؛
- مدیریت چند Tool Call، خطاها و سقف دورهای ابزار در چرخهٔ واقعی.

### ۱۹.۵. تصمیم فنی موقت برای ادامه

با توجه به گسست ثبت‌شده در بخش‌های ۱۶ و ۱۷ و موفقیت آزمایش بخش ۱۹.۲، مسیر کم‌تغییر پیشنهادی چنین تثبیت می‌شود:

1. تابع فعلی `ask_model(prompt) -> str` حفظ شود تا سازگاری مسیر فعلی Receiver از بین نرود.
2. قابلیت جدیدی در لایهٔ Client اضافه شود که ورودی پیام‌های نقش‌دار و تعاریف ابزار را بپذیرد و درخواست را به Ollama بفرستد.
3. پاسخ بومی Ollama در همان لایه به ساختار دقیق مورد انتظار AgentLoop تبدیل شود؛ تبدیل باید با کد واقعی AgentLoop و Dispatcher تطبیق داده شود، نه بر اساس حدس دربارهٔ قالب.
4. پیش از اتصال ابزارهای Workspace، یک ابزار ساختگی با تابع اجرایی محلی و بی‌خطر در Registry ثبت شود تا چرخهٔ کامل Tool Call → Dispatcher → نتیجهٔ ابزار → مدل → پاسخ نهایی آزمایش شود.
5. تا پایان موفق این آزمایش، چهار ابزار واقعی Workspace اجرا یا به مسیر مدل متصل نشوند.

این تصمیم به معنی مجوز تغییر Receiver نیست. ابتدا باید مشخص شود چگونه AgentLoop در لایهٔ فعلی Client فراخوانی می‌شود و آیا حفظ کامل Receiver با ساختار فعلی ممکن است. هر تغییر اجتناب‌ناپذیر در Receiver باید جداگانه با دلیل و diff محدود مطرح شود و پیش از اجرا تأیید کاربر را بگیرد.

### ۱۹.۶. گام اجرایی بعدی

گام بعدی، بررسی تطبیقی کدهای واقعی `AgentLoop`، `ToolRegistry` و `ToolDispatcher` با پاسخ نمونهٔ Ollama است؛ سپس طراحی و پیاده‌سازی Client سازگار و تست چرخهٔ ساختگی انجام می‌شود.

**وضعیت فایل‌ها و محیط:** کد `ollama_client.py` فقط در گفتگو دریافت و بررسی شد؛ در این مرحله هیچ فایل اجرایی محلی تغییر نکرده است. آزمایش PowerShell فقط به Ollama محلی درخواست فرستاد و ابزار ساختگی را اجرا نکرد. Receiver، دیتابیس و توکن Telegram دست‌نخورده باقی مانده‌اند. این الحاقیه فقط وضعیت و تصمیم‌های موقت را ثبت می‌کند و سند اصلی نسخهٔ ۰.۳ یا فایل‌های Library را تغییر نمی‌دهد.

## ۲۱. بررسی چرخهٔ Tool Calling در `AgentLoop`

**وضعیت: متن کامل `agent/loop.py` از سوی کاربر ارائه و بررسی شد؛ ۲۰۲۶-۱۱-۲۰.**

این بررسی بر اساس کد ارائه‌شده در گفتگو انجام شده است؛ نسخهٔ روی دیسک محیط اجرا مستقلاً Hash یا تطبیق داده نشده است.

### ۲۱.۱. قرارداد Client مورد انتظار

AgentLoop متد زیر را از Client انتظار دارد:

```python
response = self.model_client.chat(messages, tools=tools)
```

و پاسخ را با ساختار سازگار با OpenAI Chat Completions می‌خواند:

```python
response["choices"][0]["message"]
```

در نتیجه، پاسخ بومی Ollama از `/api/chat` باید در لایهٔ Client به این قرارداد تبدیل شود؛ پاسخ بومی Ollama مستقیماً همان ساختار `choices` را ندارد. بهتر است این تبدیل در Client/Adapter انجام شود و تا وقتی شواهد خلاف آن وجود ندارد، AgentLoop دست‌نخورده بماند.

### ۲۱.۲. چرخهٔ ابزار در کد ارائه‌شده

AgentLoop این مراحل را انجام می‌دهد:

1. برای هر درخواست، یک شناسهٔ کوتاه می‌سازد و پیام‌های `system` و `user` را در تاریخچه قرار می‌دهد.
2. تا سقف `max_tool_rounds)، تعریف ابزارها را از `tool_registry.definitions()` می‌گیرد؛ در فراخوانی نهایی مدل، `tools=None` می‌فرستد.
3. پاسخ مدل را از `choices[0].message` استخراج و خود پیام دستیار را به تاریخچه اضافه می‌کند.
4. اگر `tool_calls` وجود داشته باشد، نام و آرگومان هر فراخوانی را استخراج می‌کند.
5. اجرای هر ابزار را به `tool_dispatcher.execute(name, arguments)` می‌سپارد.
6. موفقیت یا خطای هر ابزار را به JSON تبدیل می‌کند و پیام دارای `role="tool"` و `tool_call_id` را به تاریخچه می‌افزاید.
7. در دور بعد، تاریخچهٔ شامل پیام دستیار و نتیجهٔ ابزار را دوباره به مدل می‌فرستد.

این ساختار از نظر ترتیب کلی پیام‌ها با چرخهٔ موردنیاز Tool Calling سازگار است. بااین‌حال، صرف مشاهدهٔ کد، اجرای موفق انتها‌به‌انتها را اثبات نمی‌کند.

### ۲۱.۳. تطبیق با Registry و Dispatcher

- AgentLoop تعریف ابزارها را با `tool_registry.definitions()` می‌گیرد؛ این با متد Registry بررسی‌شده در بخش ۱۶ هم‌خوان است.
- AgentLoop آرگومان‌های فراخوانی را به `tool_dispatcher.execute(name, arguments)` می‌دهد.
- طبق کد Dispatcher بررسی‌شده در بخش ۱۶، رشتهٔ JSON در خود Dispatcher به دیکشنری تبدیل و سپس تابع اجرایی ابزار فراخوانی می‌شود؛ بنابراین ارسال رشتهٔ خام از AgentLoop با قرارداد فعلی Dispatcher سازگار است.
- AgentLoop پیش از dispatch یک Parse جداگانه برای آرگومان‌ها انجام می‌دهد، اما نتیجهٔ آن فقط برای Logging مسیر استفاده می‌شود؛ این Parse محلی جایگزین اعتبارسنجی Dispatcher نیست.

### ۲۱.۴. رفتار سقف دورها

با مقدار پیش‌فرض `max_tool_rounds=2`، دو دور اجرای Tool Call مجاز است و پس از آن یک فراخوانی نهایی مدل بدون تعریف ابزار انجام می‌شود. اگر مدل در آن فراخوانی نهایی باز هم Tool Call برگرداند، AgentLoop پیام محدودیت را بازمی‌گرداند و آن Tool Call را اجرا نمی‌کند.

این سقف، تعداد دورها را محدود می‌کند، نه تعداد کل ابزارها؛ مدل می‌تواند در یک دور چند Tool Call تولید کند و AgentLoop همهٔ آن‌ها را به‌ترتیب اجرا می‌کند.

### ۲۱.۵. موارد باز برای تست یا تصمیم

1. **ساختار پاسخ Client:** باید ثابت شود Adapter خروجی Ollama را دقیقاً به شکل `choices[0].message` تبدیل می‌کند و شناسه‌ها و آرگومان‌های Tool Call را بدون از دست‌رفتن اطلاعات نگه می‌دارد.
2. **شناسهٔ Tool Call:** پیام برگشتی ابزار باید `tool_call_id` معتبر و متناظر داشته باشد. کد فعلی مقدار `tool_call.get("id")` را بدون بررسی خالی‌نبودن می‌فرستد.
3. **آرگومان‌های نامعتبر:** AgentLoop در Parse محلی، در صورت خطا `parsed_arguments={}` می‌گذارد، اما مقدار اصلی را به Dispatcher می‌فرستد. طبق قرارداد فعلی، Dispatcher خطای JSON یا نوع نامعتبر را مدیریت/اعلام می‌کند؛ این رفتار باید در تست چرخه پوشش داده شود.
4. **پاسخ بدون محتوا:** اگر مدل Tool Call ندهد اما `content` خالی یا تهی برگرداند، AgentLoop آن را تکمیل موفق تلقی کرده و رشتهٔ خالی بازمی‌گرداند. رفتار پاسخ خالی هنوز تعیین نشده است.
5. **علت پایان مدل:** `finish_reason` فقط در Log ثبت می‌شود. وضعیت‌هایی مانند `length` یا پاسخ ناقص فعلاً رفتار کنترلی جداگانه ندارند.
6. **چند Tool Call در یک پاسخ:** حلقه آن‌ها را به‌ترتیب اجرا می‌کند؛ تست باید اطمینان دهد برای هر فراخوانی دقیقاً یک پیام ابزار با شناسهٔ صحیح اضافه می‌شود.
7. **تعریف ابزار در فراخوانی نهایی:** کد مقدار `tools=None` را به Client می‌دهد. Adapter باید این وضعیت را به‌شکل درست به API Ollama نگاشت کند؛ مشخص شود فیلد `tools` حذف شود یا مقدار دیگری بگیرد، نه اینکه بدون بررسی فرض شود `null` پذیرفته است.
8. **تعداد کل فراخوانی‌ها:** سقف دورها به‌تنهایی تعداد Tool Callهای یک دور را محدود نمی‌کند. برای تست ساختگی فعلی این محدودیت را به‌عنوان رفتار موجود ثبت می‌کنیم؛ تغییر سیاست تعداد ابزارها تا زمان مشاهدهٔ نیاز واقعی ضروری نیست.

### ۲۱.۶. تصمیم موقت و گام بعدی

- AgentLoop، Registry و Dispatcher فعلاً قابل حفظ‌اند؛ در کد ارائه‌شده مانع قطعی برای بازنویسی AgentLoop دیده نشد.
- آداپتر Ollama باید قرارداد `chat(messages, tools=...)` و پاسخ `choices[0].message` را تأمین کند.
- پیش از اتصال چهار ابزار واقعی، یک تست یکپارچه با ابزار ساختگی `demo_lookup` اجرا شود: Tool Call تولیدشده از Ollama → اجرای تابع ساختگی از طریق Dispatcher → افزودن پیام `tool` با شناسهٔ درست → فراخوانی مجدد مدل → پاسخ نهایی متکی بر نتیجهٔ ساختگی.
- تست باید علاوه بر حالت موفق، دست‌کم خطای ابزار، آرگومان JSON نامعتبر، چند Tool Call و رسیدن به سقف دورها را پوشش دهد.
- تا موفقیت این تست، چهار ابزار واقعی Workspace به مسیر مدل متصل یا اجرا نشوند.
- فایل‌های محلی، Receiver، دیتابیس و توکن Telegram در این بررسی تغییر نکرده‌اند؛ هیچ تست اجرایی در محیط کاربر اجرا نشده است.

**جمع‌بندی:** کد AgentLoop از نظر ترتیب چرخهٔ ابزار با Registry و Dispatcher موجود هم‌راستاست. گلوگاه اصلی همچنان Client سازگار با Ollama و اثبات رفت‌وبرگشت کامل Tool Call است؛ نه بازنویسی AgentLoop. گام بعدی پس از این بررسی، دریافت و بررسی نسخه‌های فعلی `model/openrouter.py` و `model/gemini.py` برای شناخت قرارداد Client موجود و سپس طراحی Adapter Ollama با کمترین تغییر است.

## ۲۳. طرح فنی MVP برای اتصال GPT-OSS/Ollama به چرخهٔ ابزار

**وضعیت: طرح طراحی بر اساس کدها و خروجی‌های ارائه‌شده؛ هنوز پیاده‌سازی یا تست انتها‌به‌انتها انجام نشده است. تاریخ: ۲۰۲۶-۱۱-۲۰.**

### ۲۳.۱. تصمیم معماری پیشنهادی

مسیر مدل برای MVP تک‌مدلی باشد و AgentLoop موجود حفظ شود:

`Telegram → Receiver فعلی → لایهٔ اتصال/سازندهٔ AgentLoop → AgentLoop → OllamaAdapter → Ollama API`

در شاخهٔ ابزار:

`AgentLoop → ToolDispatcher → ToolRegistry → ابزار → نتیجهٔ tool → AgentLoop → OllamaAdapter → پاسخ نهایی`

- مدل هدف: `gpt-oss-20b-local:latest`.
- آدرس API: `http://localhost:11434/api/chat`.
- OpenRouter و Gemini جزو مسیر MVP نیستند.
- Registry، Dispatcher و چهار ابزار فعلی در صورت موفقیت تست‌های سازگاری حفظ شوند.
- CLI موجود در `main.py` نباید با مسیر Telegram اشتباه گرفته شود؛ فعال‌کردن CLI به‌تنهایی اتصال Telegram را ایجاد نمی‌کند.

### ۲۳.۲. مرز مسئولیت OllamaAdapter

Adapter باید قرارداد مورد انتظار AgentLoop را پیاده کند:

`chat(messages, tools=...) → response`

و پاسخ را به شکلی برگرداند که AgentLoop فعلی بتواند آن را بخواند:

`response["choices"][0]["message"]`

مسئولیت‌های Adapter:
1. تبدیل تاریخچهٔ نقش‌دار AgentLoop به قالب پیام‌های API بومی Ollama؛
2. تبدیل تعریف ابزارهای Registry به قالب ابزارهای Ollama؛
3. ارسال درخواست به `/api/chat` با `stream=false` در نسخهٔ اولیه؛
4. حفظ محتوای پیام دستیار، شناسهٔ Tool Call، نام ابزار و آرگومان‌ها هنگام تبدیل پاسخ؛
5. تبدیل Tool Call بومی Ollama به ساختار سازگار با AgentLoop؛
6. تبدیل درست پیام‌های `role="tool"` و نتیجهٔ ابزار برای درخواست بعدی Ollama؛
7. مدیریت خطاهای HTTP، اتصال، timeout، پاسخ نامعتبر و پاسخ فاقد پیام؛
8. حذف یا تنظیم صحیح فیلد `tools` در فراخوانی نهایی که AgentLoop آن را با `tools=None` انجام می‌دهد.

**قید:** شکل دقیق نگاشت پیام‌های assistant/tool و Tool Call باید با مستندات و تست واقعی نسخهٔ نصب‌شدهٔ Ollama تأیید شود؛ صرف شباهت مفهومی قالب‌ها کافی نیست. آزمایش مستقیم کاربر فقط تولید Tool Call در پاسخ Ollama را اثبات کرده و هنوز رفت‌وبرگشت نتیجهٔ ابزار را اثبات نکرده است.

### ۲۳.۳. سازگاری با تابع فعلی `ask_model`

تابع فعلی `ask_model(prompt) -> str` در `ollama_client.py` یک قرارداد ساده و متنی دارد و Receiver فعلی از آن استفاده می‌کند. این تابع نباید بدون بررسی تمام مصرف‌کنندگانش به API ساختاریافته تبدیل یا حذف شود.

پیشنهاد کم‌ریسک:
- قابلیت `chat(messages, tools=None)` به‌صورت یک Client/Adapter ساختاریافته اضافه شود؛
- `ask_model(prompt)` تا تعیین تکلیف Receiver حفظ شود؛
- در صورت امکان، هر دو مسیر از توابع مشترک ارسال درخواست، تنظیمات مدل و مدیریت خطا استفاده کنند تا منطق HTTP دو بار پیاده‌سازی نشود؛
- نام فایل، کلاس و محل نهایی ساخت Client پس از مشاهدهٔ importها و ساختار واقعی package تثبیت شود.

### ۲۳.۴. راهبرد اتصال Telegram بدون بازنویسی زودهنگام Receiver

اطلاعات فعلی نشان می‌دهد Receiver مستقیماً `ask_model(message_text)` را صدا می‌زند، درحالی‌که AgentLoop فعلاً در `main.py` و مسیر CLI ساخته می‌شود. بنابراین هنوز یک نقطهٔ اتصال مشترک و اثبات‌شده نداریم.

ترتیب بررسی:

2. بررسی اینکه آیا می‌توان وابستگی مدل را در همان مرز موجود با یک تابع واسط یا service قابل تزریق جایگزین کرد، بدون تغییر مسئولیت‌های Receiver؛

## ۲۵. بررسی قرارداد فعلی `ollama_client.py` و جهت طراحی سرویس مدل

**وضعیت: کد کامل تابع و فایل `ollama_client.py` از سوی کاربر ارائه و بررسی شد؛ ۲۰۲۶-۱۱-۲۰.**  
**دامنهٔ بررسی:** فقط کد درج‌شده در گفتگو؛ نسخهٔ روی دیسک مستقلاً تطبیق داده نشده است.

### ۲۵.۱. رفتار فعلی فایل

فایل `ollama_client.py` در وضعیت فعلی یک کلاینت متنی و ساده برای Ollama است:

1. نام مدل و حالت Thinking را از `config.py` می‌خواند.
2. ورودی را به یک پیام با نقش `user` تبدیل می‌کند؛ تاریخچهٔ مکالمه یا پیام‌های چندنقشی دریافت نمی‌کند.
3. درخواست غیرجریانی (`stream=False`) به endpoint بومی `/api/chat` می‌فرستد.
4. بر اساس `THINKING_MODE` مقدار `think` را تنظیم می‌کند؛ در حالت `auto` برای مدل‌هایی که نامشان با `qwen` شروع می‌شود مقدار `False` می‌گذارد.
5. زمان پاسخ را ثبت می‌کند و مقدار `result["message"]["content"]` را به‌صورت رشته برمی‌گرداند.
6. خطای HTTP را به `RuntimeError` تبدیل می‌کند. سایر خطاهای شبکه، timeout، JSON نامعتبر یا ساختار پاسخ ناقص در این فایل به‌طور اختصاصی مدیریت نشده‌اند و به فراخواننده منتقل می‌شوند.

مقدار timeout فعلی `2000` ثانیه است. این مقدار در این مرحله صرفاً ثبت می‌شود و بدون تست و تصمیم جداگانه تغییر نخواهد کرد.

### ۲۵.۲. قابلیت‌ها و محدودیت‌های مهم برای AgentLoop

- تابع `ask_model(prompt) -> str` با نیاز فعلی Receiver سازگار است.
- این رابط به‌تنهایی برای AgentLoop کافی نیست؛ AgentLoop به `chat(messages, tools=...)` و پاسخ ساختاریافتهٔ سازگار با قرارداد فعلی خود نیاز دارد.
- Client فعلی ابزارها را به Ollama معرفی نمی‌کند، Tool Call را استخراج/تبدیل نمی‌کند و پیام‌های `assistant` و `tool` را در تاریخچه رفت‌وبرگشت نمی‌دهد.
- بنابراین افزودن Tool Calling به معنی تغییر معنای تابع فعلی یا تحمیل ساختار AgentLoop به Receiver نیست؛ باید یک مسیر ساختاریافتهٔ مستقل برای AgentLoop فراهم شود.
- تنظیمات مدل و Thinking موجود باید تا حد امکان از منبع فعلی خود استفاده شوند؛ از تعریف دوباره یا واگراشدن تنظیمات در چند فایل پرهیز شود.

### ۲۵.۳. تصمیم طراحی مورد توافق برای گام بعد

1. فایل `ollama_client.py` در این مرحله دست‌نخورده می‌ماند و تابع متنی فعلی آن حفظ می‌شود.
2. Receiver همچنان فقط به قرارداد `ask_model(prompt) -> str` وابسته خواهد بود؛ جزئیات Ollama، AgentLoop، Registry و Dispatcher به Receiver نشت نمی‌کند.
3. یک ماژول مستقل با نام پیشنهادی `ilan_model_service.py` به‌عنوان façade/service در نظر گرفته می‌شود. این فایل در بالای خود docstring روشن خواهد داشت که نقش ماژول، مسیر ورود پیام متنی، ساخت/نگهداری AgentLoop و بازگرداندن پاسخ نهایی به‌صورت رشته چیست؛ همچنین مسئولیت‌ها و موارد خارج از دامنه‌اش را توضیح می‌دهد.
4. سرویس از AgentLoop موجود و یک Ollama adapter سازگار با قرارداد آن استفاده خواهد کرد؛ ساخت دقیق وابستگی‌ها و عمر نمونه‌ها باید پس از بازبینی importها، سازنده‌ها و قراردادهای واقعی فایل‌های موجود تعیین شود.
5. مسیر متنی مستقیم `ollama_client.ask_model` تا زمان جابه‌جایی کنترل‌شدهٔ نقطهٔ ورود Receiver حفظ می‌شود؛ ایجاد سرویس جدید به‌تنهایی به معنی تغییر یا فعال‌سازی Receiver نیست.
6. هیچ ابزار واقعی Workspace تا زمان موفقیت تست یکپارچهٔ ساختگی به مدل معرفی نمی‌شود.

### ۲۵.۴. قیدهای بازیابی و تکرار عملیات

- retry فعلی Receiver برای درخواست متنی مدل، پس از خطا کل پردازش پیام را از نو انجام می‌دهد.
- این رفتار با Tool Callهای جانبی یکسان نیست: ابزار صرفاً خواندنی مانند `read_file` با ابزار تغییردهنده‌ای مانند `apply_patch` یا ابزار اجرای تست، پیامد تکرار متفاوتی دارد.
- سیاست بازیابی باید بر اساس نوع اثر ابزار، شناسهٔ پایدار عملیات و مرحله‌ای که پیش از توقف ثبت شده طراحی شود؛ نباید یک برچسب کلی «idempotent» به همهٔ ابزارها نسبت داد.
- پیش از فعال‌سازی ابزارهای تغییردهنده، وضعیت‌های «درخواست ثبت‌شده»، «فراخوانی ابزار آغازشده»، «نتیجهٔ ابزار ثبت‌شده» و «پاسخ نهایی ذخیره‌شده» باید در حد لازم قابل بازیابی باشند یا سیاست امن و صریح دیگری برای حالت نامعلوم اجرا تعریف شود.
- این بخش هنوز طراحی تفصیلی یا پیاده‌سازی‌شده نیست؛ Receiver و دیتابیس فعلی تغییر نکرده‌اند.

### ۲۵.۵. گام بررسی بعدی پیش از نوشتن فایل جدید

پیش از تولید `ilan_model_service.py` باید از روی نسخهٔ واقعی کد، این موارد تأیید شوند:

1. امضای سازنده و ورودی‌های `AgentLoop`؛
2. قرارداد دقیق `model_client` و محل پیاده‌سازی Adapter؛
3. نحوهٔ ساخت و چرخهٔ عمر `ToolRegistry` و `ToolDispatcher`؛
4. نحوهٔ تأمین system prompt و تنظیمات AgentLoop؛
5. import path/package structure برای جلوگیری از import cycle؛
6. callbackهای تأیید ابزارها در مسیر Telegram، خصوصاً برای `apply_patch` و `run_tests`.

پس از این بازبینی، فایل مستقل با docstring توضیحی در ابتدای آن طراحی و ابتدا با ابزار ساختگی و بی‌خطر تست می‌شود. هنوز فایل جدیدی ساخته یا Receiver/Client موجودی تغییر داده نشده است.

**جمع‌بندی:** `ollama_client.py` فعلی یک رابط متنی سالم و ساده برای مسیر فعلی است، نه Client ابزارمحور AgentLoop. حفظ آن و افزودن یک façade مستقل، کم‌تغییرترین جهت فعلی است؛ اما نوشتن فایل سرویس باید پس از تطبیق قراردادهای واقعی AgentLoop و ابزارها انجام شود تا کد حدسی یا importهای نادرست تولید نشود.

## ۲۶. بررسی قرارداد AgentLoop ارائه‌شده و نکات اتصال

**وضعیت: کد کامل کلاس `AgentLoop` از سوی کاربر ارائه و بررسی شد؛ ۲۰۲۶-۱۱-۲۰.**  
**دامنهٔ بررسی:** فقط کد درج‌شده در گفتگو؛ تطبیق با نسخهٔ مخزن/دیسک هنوز انجام نشده است.

### ۲۶.۱. قراردادهای قطعی قابل مشاهده

سازندهٔ `AgentLoop` این وابستگی‌ها را دریافت می‌کند:

- `model_client`
- `tool_registry`
- `tool_dispatcher`
- `system_prompt` با مقدار پیش‌فرض
- `max_tool_rounds` با مقدار پیش‌فرض ۲

رابط مورد انتظار مدل:

`model_client.chat(messages, tools=tools)`

پاسخ مدل باید ساختاری سازگار با `response["choices"][0]["message"]` داشته باشد. پیام‌های مکالمه به شکل ساختاریافته و با نقش‌های `system`، `user`، `assistant` و `tool` نگهداری می‌شوند.

رابط رجیستری:

`tool_registry.definitions()`

رابط اجرا:

`tool_dispatcher.execute(name, arguments)`

رابط بیرونی AgentLoop:

`AgentLoop.run(user_message) -> str`

بنابراین خروجی آن از نظر نوع داده با façade موردنظر برای حفظ قرارداد متنی Receiver سازگار است.

### ۲۶.۲. رفتار چرخهٔ ابزار

- تعداد فراخوانی‌های مدل حداکثر `max_tool_rounds + 1` است.
- تعریف ابزارها فقط تا پیش از دور نهایی به مدل داده می‌شود؛ در دور نهایی `tools=None` است.
- پس از هر پاسخ دستیار دارای Tool Call، هر فراخوانی ابزار اجرا و نتیجه با نقش `tool` و `tool_call_id` متناظر به تاریخچه اضافه می‌شود.
- خطای اجرای هر ابزار به‌صورت یک نتیجهٔ خطا به مدل بازگردانده می‌شود؛ خطای فراخوانی مدل ثبت و دوباره پرتاب می‌شود.
- اگر پاسخ مدل Tool Call نداشته باشد، محتوای دستیار به‌عنوان پاسخ نهایی برگردانده می‌شود.
- اگر در آخرین دور همچنان Tool Call وجود داشته باشد، متن محدودیت دورها برگردانده می‌شود.

### ۲۶.۳. نکتهٔ مهم دربارهٔ آرگومان ابزار

کد، `arguments` را برای ثبت مسیر و گزارش‌گیری به `parsed_arguments` تبدیل می‌کند، اما خود مقدار اصلی `arguments` را به `tool_dispatcher.execute` می‌دهد.

این به‌تنهایی اثبات اشکال نیست: در بررسی قبلیِ `tools/dispatcher.py` ثبت شده بود که Dispatcher رشتهٔ JSON را parse می‌کند. بااین‌حال، باید نسخهٔ دقیق Dispatcher و نوع دادهٔ واقعی `arguments` در پاسخ Ollama تطبیق داده شود؛ به‌ویژه اگر آرگومان‌ها از قبل dict باشند یا JSON نامعتبر/غیرشیء باشند. نباید AgentLoop یا Dispatcher را بر اساس حدس تغییر داد.

### ۲۶.۴. ملاحظات و ریسک‌های باز

1. در صورت نبودن `choices` خطا ایجاد می‌شود؛ اما شکل و نوع `choices[0]` و `message` به‌طور کامل اعتبارسنجی نمی‌شود.
2. `finish_reason` فقط ثبت می‌شود و در تصمیم‌گیری چرخه نقشی ندارد.
3. Tool Call ناقص، شناسهٔ خالی یا نام ابزار نامعتبر باید در تست‌های سازگاری پوشش داده شود.
4. اگر چند Tool Call در یک پاسخ باشند، حلقه همه را به‌ترتیب اجرا می‌کند؛ سیاست توقف پس از شکست یک ابزار وجود ندارد و نتیجهٔ خطا به مدل تحویل می‌شود.
5. محدودیت دورها جلوی حلقهٔ بی‌پایان را می‌گیرد، اما وضعیت عملیات را برای بازیابی پس از توقف پردازه ذخیره نمی‌کند.
6. در این کد، شناسهٔ درخواست فقط برای log است و شناسهٔ پایدار/قابل‌بازیابی عملیات نیست.
7. مدیریت خطا و retry در Receiver باید با امکان اجرای دوبارهٔ ابزارهای تغییردهنده سنجیده شود؛ صرف داشتن request_id در log، مانع اجرای تکراری نیست.

### ۲۶.۵. تصمیم ادامهٔ بررسی

- قرارداد کلی AgentLoop برای طراحی Adapter و façade اکنون روشن است؛ لازم نیست کاربر دوباره همین فایل را ارسال کند.
- پیش از نوشتن فایل جدید، باید نسخهٔ دقیق `ToolRegistry`، `ToolDispatcher` و محل ساخت و اتصال آن‌ها بررسی شود.
- همچنین باید مسیر import واقعی و محل ساخت AgentLoop بررسی شود تا وابستگی‌ها دوباره ساخته نشوند یا چرخهٔ import ایجاد نشود.
- `AgentLoop` فعلاً دست‌نخورده می‌ماند. اصلاح احتمالی اعتبارسنجی پاسخ، آرگومان‌ها یا بازیابی عملیات به‌عنوان کار جداگانه و پس از دیدن زنجیرهٔ کامل بررسی می‌شود.
- هیچ فایل اجرایی تغییر نکرده و هیچ تستی در محیط کاربر اجرا نشده است.

## ۲۷. بررسی قرارداد فعلی ToolDispatcher

**وضعیت: کد کامل کلاس `ToolDispatcher` از سوی کاربر ارائه و بررسی شد؛ ۲۰۲۶-۱۱-۲۰.**  
**دامنهٔ بررسی:** فقط قطعهٔ ارائه‌شده در گفتگو؛ تطبیق با نسخهٔ روی دیسک/مخزن انجام نشده است.

### ۲۷.۱. قرارداد و رفتار قابل مشاهده

- سازنده یک `registry` دریافت می‌کند و آن را نگه می‌دارد.
- `execute(name, arguments)` ابزار را با `registry.get(name)` بازیابی می‌کند.
- اگر `arguments` رشته باشد، با `json.loads` به ساختار Python تبدیل می‌شود.
- در ادامه فقط `dict` پذیرفته می‌شود؛ سایر انواع با `ValueError` رد می‌شوند.
- تابع اجرایی ابزار با `tool["execute"](arguments)` فراخوانی می‌شود.
- اگر خروجی سطح اول dataclass باشد، با `asdict` تبدیل می‌شود؛ اگر `Path` باشد، به رشته تبدیل می‌شود.
- در غیر این صورت خروجی بدون تبدیل بیشتر بازگردانده می‌شود.

### ۲۷.۲. تطبیق با AgentLoop

قرارداد فراخوانی AgentLoop یعنی `tool_dispatcher.execute(name, arguments)` با این Dispatcher سازگار است:

- JSON string به‌وسیلهٔ Dispatcher parse می‌شود.
- dict از قبل parse‌شده نیز پذیرفته می‌شود.
- بنابراین ارسال `arguments` خام از AgentLoop به‌خودی‌خود اشکال نیست و `parsed_arguments` در AgentLoop فعلاً برای log مسیر/گزارش‌گیری استفاده می‌شود.
- خطای JSON نامعتبر، نوع آرگومان نامعتبر یا خطای اجرای ابزار از Dispatcher بیرون می‌آید؛ AgentLoop آن را می‌گیرد و نتیجهٔ ناموفق را در پیام `tool` به مدل برمی‌گرداند.

### ۲۷.۳. موارد باز و محدودیت‌ها

1. اگر `registry.get(name)` برای نام ناشناخته مقدار `None` بدهد، این فایل خطای اختصاصی/روشن برای ابزار ناشناخته تولید نمی‌کند؛ تلاش برای دسترسی به `tool["execute"]` احتمالاً `TypeError` ایجاد می‌کند. رفتار واقعی به قرارداد Registry وابسته است.
2. تبدیل خروجی فقط برای dataclass یا Path در سطح اول انجام می‌شود. تبدیل بازگشتی ساختارهای تو‌در‌تو در این قطعه دیده نمی‌شود؛ باید نوع خروجی ابزارهای واقعی بررسی شود.
3. `json.loads` می‌تواند انواع JSON غیر از object را نیز parse کند؛ سپس شرط dict آن‌ها را رد می‌کند که رفتار محافظه‌کارانه و روشن است.
4. schema پارامترها در این کلاس اعتبارسنجی نمی‌شود؛ باید بررسی شود آیا Registry یا ابزارها این مسئولیت را بر عهده دارند.
5. کنترل مجوز، تأیید کاربر، ثبت وضعیت عملیات، جلوگیری از اجرای تکراری یا ثبت Trace در این کلاس دیده نمی‌شود. این‌ها ممکن است در لایه‌های دیگر باشند و هنوز دربارهٔ کل زنجیره نتیجه‌گیری نمی‌کنیم.

### ۲۷.۴. تصمیم ادامهٔ بررسی

- در این مرحله هیچ تغییری در AgentLoop یا ToolDispatcher لازم تشخیص داده نشد.
- برای تکمیل زنجیرهٔ ساخت ابزار، فایل Registry لازم است؛ به‌ویژه پیاده‌سازی `get` و `definitions` و نحوهٔ ثبت چهار ابزار.
- پس از Registry باید محل ساخت و اتصال Registry، Dispatcher و AgentLoop در فایل اجرایی بررسی شود.
- هنوز هیچ فایل اجرایی تغییر نکرده و هیچ تستی در محیط کاربر اجرا نشده است.


## ۲۸. بررسی قرارداد فعلی ToolRegistry

### کد و رفتار مشاهده‌شده
کلاس `ToolRegistry` یک دیکشنری داخلی به نام `_tools` نگه می‌دارد و سه رابط اصلی دارد:

- `register(name, description, parameters, execute)`: ابزار را با این چهار فیلد ثبت می‌کند. اگر نام از قبل ثبت شده باشد، `ValueError` ایجاد می‌کند. اعتبارسنجی مستقل برای خالی‌بودن نام/توضیح، نوع ورودی‌ها یا صحت schema در همین کلاس دیده نمی‌شود.
- `get(name)`: رکورد ابزار را مستقیماً از دیکشنری برمی‌گرداند. نام ثبت‌نشده باعث `KeyError` می‌شود؛ بنابراین برخلاف احتمال مطرح‌شده در بررسی اولیه Dispatcher، خروجی عادی این متد برای ابزار ناشناخته `None` نیست.
- `definitions()`: برای هر ابزار یک تعریف با ساختار `{"type": "function", "function": {"name": ..., "description": ..., "parameters": ...}}` تولید می‌کند. تابع اجرایی `execute` در تعریف ارسالی به مدل قرار نمی‌گیرد.

### تطبیق با AgentLoop و ToolDispatcher
- AgentLoop از `definitions()` برای معرفی ابزارها به model client استفاده می‌کند.
- ToolDispatcher از `get(name)` برای بازیابی رکورد و سپس اجرای `tool["execute"](arguments)` استفاده می‌کند.
- این جداسازی میان metadata قابل‌ارائه به مدل و callable اجرایی در Registry، از نظر مسئولیت‌ها منسجم است.
- ساختار `definitions()` با قالب OpenAI-compatible Function Calling هم‌خوان است؛ اما این به‌تنهایی سازگاری واقعی با Ollama را ثابت نمی‌کند. باید قرارداد `model_client.chat(messages, tools=tools)` و نحوهٔ ارسال درخواست HTTP آن بررسی شود تا مشخص شود تبدیل لازم است یا خیر.
- schemaهای `parameters` بدون اعتبارسنجی یا تبدیل عبور داده می‌شوند؛ در نتیجه صحت و سازگاری آن‌ها به محل تعریف schemaها و model client وابسته است.

### یافته‌ها و موارد باز
1. جلوگیری از ثبت نام تکراری در Registry انجام می‌شود.
2. برای نام ناشناخته، `get()` خطای `KeyError` می‌دهد؛ Dispatcher این خطا را به‌عنوان خطای اجرای ابزار به AgentLoop منتقل می‌کند.
3. Registry schema پارامترها را اعتبارسنجی نمی‌کند؛ هنوز باید محل ثبت ابزارها و schemaهای واقعی بررسی شود.
4. سازگاری قالب definitions با endpoint و مدل Ollama هنوز تأیید انتها‌به‌انتها نشده است.
5. در کلاس ارائه‌شده نشانه‌ای از سیاست مجوزدهی، تأیید کاربر، ثبت وضعیت عملیات یا idempotency دیده نمی‌شود؛ این موارد ممکن است در لایه‌های دیگر قرار داشته باشند و فعلاً دربارهٔ کل سامانه نتیجه‌گیری نمی‌شود.

### تصمیم و گام بعدی
- فعلاً هیچ تغییری در `ToolRegistry`، `ToolDispatcher` یا `AgentLoop` پیشنهاد نمی‌شود.
- گام بعدی بررسی فایل/محل ساخت و اتصال `model_client`، `AgentLoop`، `ToolRegistry` و `ToolDispatcher` و همچنین محل ثبت ابزارهاست.
- پس از مشاهدهٔ آن مسیر واقعی، قرارداد model client و نیاز یا عدم نیاز به adapter مخصوص Ollama مشخص می‌شود.
- تا پیش از این بررسی و تست یکپارچه با ابزارهای ساختگی و بی‌خطر، ابزارهای واقعی Workspace نباید از مسیر Telegram در اختیار مدل قرار گیرند.

5. اینکه اجرای Telegram چگونه قرار است به AgentLoop متصل شود و callbackهای تعاملی مجوز/تأیید patch در آن محیط چگونه رفتار خواهند کرد.

### تصمیم و گام بعدی
- فعلاً `main.py`، AgentLoop، Registry، Dispatcher و clientهای موجود تغییر نکنند.
- پیش از ساخت `ilan_model_service.py`، کد کامل فایل‌های `model/openrouter.py` و `model/gemini.py` بررسی شود.
- پس از بررسی قرارداد clientها، مسیر افزودن Ollama یا façade مشترک تعیین شود؛ نباید فرض کرد هر سه provider قرارداد داخلی یکسانی دارند.

- ابزارهای واقعی Workspace تا پیش از تست یکپارچه با ابزارهای ساختگی و بی‌خطر، نباید از مسیر جدید Telegram به مدل عرضه شوند.

## ۳۳. تصمیم نهایی دربارهٔ اختیار اجرای `apply_patch` و اتصال Telegram به AgentLoop

**تصمیم صریح کاربر در ۲۰۲۶-۱۱-۲۰:**

برای تغییر فایل‌هایی که ایگور در قالب یک مأموریت مشخص به ایلان محول می‌کند، تأیید جداگانهٔ کاربر پیش از اجرای `apply_patch` لازم نیست. ایلان مجاز است تغییر را مستقیماً اعمال کند و نباید برای تأیید Diff در تلگرام متوقف بماند.

### قاعدهٔ اجرایی

1. ایگور مأموریت را با هدف، محدودهٔ فایل‌ها/تغییرات و معیار پذیرش مشخص می‌کند.
2. ایلان می‌تواند Diff را برای تحلیل داخلی و کنترل تغییر بررسی کند؛ نمایش Diff برای کاربر و اخذ تأیید پیش‌شرط اجرا نیست.
3. ایلان تغییرات را در محدودهٔ همان مأموریت اعمال می‌کند.
4. ایلان باید نتیجهٔ واقعی را گزارش کند: وضعیت اجرا، مسیر فایل‌های تغییرکرده، خلاصهٔ تغییر، نتیجهٔ تست‌ها و خطاهای رخ‌داده.
5. ایگور تغییرات و شواهد اجرا را مستقلاً بررسی می‌کند و در صورت نیاز مأموریت اصلاحی بعدی می‌دهد.
6. این اختیار به معنای اختیار مستقل ایلان برای تغییر اهداف پروژه، گسترش دامنهٔ مأموریت یا انجام اقدامات نامرتبط نیست. تصمیم‌گیر نهایی دربارهٔ جهت پروژه و تصمیم‌های مهم همچنان کاربر است.

### اثر بر پیاده‌سازی فعلی `apply_patch`

- نسخهٔ فعلی `register_apply_patch(registry, file_tools, approval_callback)` پیش از اعمال patch، `approval_callback(preview)` را فراخوانی می‌کند و در صورت رد، عملیات را متوقف می‌سازد.
- در مسیر اجرای مأموریت‌های ایگور از طریق Telegram، این توقف تعاملی باید حذف شود؛ ایلان پس از تولید/بررسی patch آن را بدون تأیید جداگانهٔ کاربر اعمال می‌کند.
- در نتیجه، طراحی Telegram نباید برای `apply_patch` سازوکار pending approval، ارسال Diff برای تأیید یا انتظار پاسخ کاربر ایجاد کند.
- کنترل محدودهٔ مأموریت باید در دستور و قرارداد اجرایی ایگور/AgentLoop حفظ شود. این تصمیم مجوز تغییر نامحدود Workspace یا تغییر خودسرانهٔ مأموریت نیست.
- این تصمیم فقط دربارهٔ تأیید کاربر برای `apply_patch` است و به‌خودی‌خود سایر کنترل‌ها یا مجوزهای ابزارها، از جمله سیاست اجرای پروفایل‌های `run_tests`، را تغییر نمی‌دهد.

### اصلاح منشأ تنظیمات Ollama

در ادامهٔ بررسی، کاربر تأیید کرد که مقادیر زیر متعلق به فایل `C:\\Ilan-Bridge\\config.py` هستند:
- `MODEL_NAME = "gpt-oss-20b-local:latest"`
- `THINKING_MODE = "auto"`

این دو مقدار فعلاً تنظیمات Bridge/Receiver هستند؛ نباید آن‌ها را بدون تصمیم و اتصال صریح، تنظیمات داخلی `ilan-bootstrap` یا AgentLoop فرض کرد. فایل `C:\\Ilan-Bridge\\ollama_client.py` نیز کلاینت متنی فعلی با رابط `ask_model(prompt) -> str` است و باید برای سازگاری با AgentLoop، کلاینت مستقل جدید ساخته شود؛ قرارداد کلاینت قدیمی بی‌دلیل تغییر نکند.

از فایل ارائه‌شده مشخص است که کلاینت قدیمی از `http://localhost:11434/api/chat` و timeout برابر ۲۰۰۰ ثانیه استفاده می‌کند. این مقادیر شواهد مربوط به Bridge هستند و استفاده از آن‌ها در client جدید باید آگاهانه و صریح باشد، نه از طریق فرض اشتراک پیکربندی.

### ملاحظهٔ مهم دربارهٔ Retry و عملیات دارای اثر جانبی

Receiver فعلی پس از خطای مدل، پیام را برای تلاش مجدد ثبت می‌کند. AgentLoop نیز ممکن است پیش از بروز خطا یک یا چند ابزار را اجرا کرده باشد. بنابراین اتصال جدید نباید بدون بررسی، کل مأموریت را پس از هر خطا از ابتدا اجرا کند؛ در غیر این صورت امکان اجرای دوبارهٔ patch یا سایر عملیات دارای اثر جانبی وجود دارد. طراحی سرویس باید وضعیت اجرا و مرحلهٔ تکمیل را طوری مدیریت کند که retry شبکه/ارسال پاسخ، اجرای مجدد ابزارهای قبلاً انجام‌شده را سبب نشود. این مورد باید در تست یکپارچه پوشش داده شود.

### وضعیت و گام بعدی

- تصمیم حذف تأیید جداگانهٔ کاربر برای `apply_patch` قطعی است.
- طراحی MVP باید مسیر مستقیم Telegram → Ilan Service → AgentLoop → Ollama Agent Client → Dispatcher/Registry → ابزارها را دنبال کند.
- Receiver همچنان مسئول دریافت/صف/ذخیره و ارسال تلگرام باقی می‌ماند؛ منطق AgentLoop در سرویس مستقل قرار می‌گیرد.
- ابتدا client مستقل Ollama با قرارداد `chat(messages, tools=None)` و پاسخ سازگار با AgentLoop ساخته و با تست‌های ساختگی/بی‌خطر بررسی شود.
- سپس اتصال واقعی AgentLoop و چهار ابزار موجود آزموده شود؛ به‌ویژه مسیر اعمال patch بدون تأیید تعاملی و جلوگیری از اجرای تکراری عملیات.
- این الحاقیه به‌روزرسانی شد؛ سند اصلی نسخهٔ ۰.۳ همچنان جداگانه و بدون تغییر باقی می‌ماند.

## 35. ثبت نتایج بررسی محیط WSL، Ollama و کدهای موجود

### 35.1. وضعیت Ollama در Windows

بر اساس خروجی PowerShell:

- فرمان `ollama list` پنج مدل نصب‌شده را نشان داد:
  - `devstral-q4kl:latest`
  - `gpt-oss-20b-local:latest`
  - `qwen35-local:latest`
  - `gemma3:4b`
  - `qwen3.5:4b`

- درخواست محلی به `http://127.0.0.1:11434/api/tags` موفق شد و هر پنج مدل را از API برگرداند؛ پس API محلی Ollama روی Windows فعال و پاسخ‌گو است.
- پورت TCP شمارهٔ `11434` در وضعیت Listen و فقط روی `127.0.0.1` مشاهده شد؛ PID گزارش‌شده `14320` بود.
- بنابراین شواهد فعلی نشان می‌دهد Ollama در Windows در دسترس است، اما listener آن فقط Loopback ویندوز را می‌پذیرد. هنوز هیچ دسترسی شبکه‌ای از WSL به این سرویس برقرار نشده است.

### 35.2. آزمون اتصال WSL به Ollama ویندوز

- آدرس nameserver/میزبان Windows که از `/etc/resolv.conf` در WSL استخراج شد: `172.24.32.1`.
- درخواست از WSL به `http://172.24.32.1:11434/api/tags` با Timeout پنج‌ثانیه‌ای شکست خورد.
- درخواست قبلی WSL به `http://localhost:11434/api/tags` نیز با Connection refused شکست خورده بود.
- این نتایج با محدودبودن listener ویندوز به `127.0.0.1` سازگارند؛ علت دقیق Timeout در مسیر میزبان/شبکه هنوز جداگانه اثبات نشده است.
- **نتیجه:** محل سرویس Ollama روی Windows و سلامت API محلی تأیید شده؛ دسترسی AgentLoop/Receiver در WSL به آن هنوز حل‌نشده است.
- هیچ تنظیمی مانند `OLLAMA_HOST=0.0.0.0`، قانون Firewall یا پیکربندی شبکه تغییر نکرده است.

### 35.3. وضعیت Windows Firewall

خروجی `Get-NetFirewallProfile` نشان داد هر سه پروفایل Domain، Private و Public فعال‌اند. مقدار `DefaultInboundAction` در هر سه `NotConfigured` است.

این مقدار به‌تنهایی سیاست مؤثر ورودی را مشخص نمی‌کند؛ ممکن است سیاست مؤثر از تنظیمات دیگر یا Group Policy حاصل شود. بنابراین از این خروجی نمی‌توان نتیجه گرفت پورت 11434 مجاز یا مسدود است. هیچ قانون Firewall تغییر نکرده است.

- **محدودیت نتیجه:** وجود پوشهٔ `.venv` و symlink به‌تنهایی کامل‌بودن یا فعال‌بودن محیط مجازی و نصب بودن وابستگی‌ها را ثابت نمی‌کند. `sys.prefix`، `pyvenv.cfg`، دسترسی pip و وابستگی‌های موردنیاز هر پروژه هنوز باید در همان محیط بررسی شوند.
- نبود pip در Python سراسری قبلاً مشاهده شده بود؛ این موضوع به‌تنهایی وضعیت pip داخل هر محیط پروژه را تعیین نمی‌کند.

## ۳۶. بررسی قرارداد AgentLoop، ToolDispatcher و نقطهٔ اتصال برنامه

**منبع بررسی:** کدهای ارسالی کاربر در تاریخ ۲۰۲۶-۱۱-۲۰ برای:
- `ilan-bootstrap/main.py`
- `ilan-bootstrap/agent/loop.py`
- `ilan-bootstrap/tools/dispatcher.py`

### یافته‌های قطعی از کد

1. **قرارداد فراخوانی مدل در AgentLoop**
   - AgentLoop متد `model_client.chat(messages, tools=tools)` را فراخوانی می‌کند.
   - پاسخ مورد انتظار شامل `choices[0].message` است.
   - پیام دستیار ممکن است `tool_calls` داشته باشد؛ هر فراخوانی شامل `function.name` و `function.arguments` است.
   - پس client مستقل Ollama برای AgentLoop باید همین قرارداد را رعایت کند؛ قرارداد متنی `ask_model(prompt) -> str` در Bridge به‌تنهایی کافی نیست.

2. **چرخهٔ ابزار**
   - AgentLoop پیام دستیار را به تاریخچه اضافه می‌کند.
   - برای هر Tool Call، آرگومان‌ها را parse و سپس `tool_dispatcher.execute(name, arguments)` را فراخوانی می‌کند.
   - نتیجهٔ ابزار با نقش `tool`، شناسهٔ `tool_call_id` و محتوای JSON به تاریخچه افزوده می‌شود.
   - سپس در دور بعدی، تاریخچه همراه با ابزارهای قابل‌استفاده به مدل فرستاده می‌شود.
   - Dispatcher ابزار را از Registry می‌گیرد، آرگومان رشته‌ای را JSON-decode می‌کند، دیکشنری بودن آن را بررسی می‌کند و تابع اجرایی ابزار را فراخوانی می‌کند. خروجی dataclass و Path را قابل‌انتقال می‌کند.

3. **محدودیت دور ابزار**
   - مقدار پیش‌فرض `max_tool_rounds=2` است.
   - حلقه حداکثر سه فراخوانی مدل انجام می‌دهد: دو دوری که ابزارها در اختیار مدل هستند و یک فراخوانی نهایی بدون ابزار.
   - اگر مدل در دور نهایی باز هم Tool Call برگرداند، AgentLoop به‌جای اجرای آن‌ها پیام محدودیت را برمی‌گرداند.
   - این سقف فعلی برای MVP یک محدودیت اجرایی مشخص است و باید هنگام طراحی مأموریت‌های چندمرحله‌ای آگاهانه حفظ یا تغییر داده شود؛ فعلاً تغییری اعمال نشده است.

4. **حافظه و دامنهٔ تاریخچه**
   - فهرست `messages` داخل هر بار اجرای `run()` ساخته می‌شود و فقط همان درخواست را پوشش می‌دهد.
   - درخواست بعدی از پیام system و user جدید آغاز می‌شود؛ حافظهٔ مکالمهٔ پایدار یا بازیابی تاریخچه در این کلاس وجود ندارد.
   - نگه‌داری وضعیت مأموریت/گفتگو برای Telegram باید بیرون از AgentLoop یا با توسعهٔ کنترل‌شدهٔ آن طراحی شود؛ نباید فرض کنیم AgentLoop فعلی خودش این کار را انجام می‌دهد.

5. **خطاها و retry**
   - خطای فراخوانی مدل log و دوباره raise می‌شود؛ retry خودکار در AgentLoop وجود ندارد.
   - خطای اجرای ابزار catch می‌شود و به‌صورت نتیجهٔ ناموفق شامل نوع خطا و پیام آن به مدل بازگردانده می‌شود.
   - اجرای چند Tool Call در یک پیام به‌ترتیب انجام می‌شود. اگر یک ابزار اثر جانبی ایجاد کند و ابزار بعدی یا فراخوانی مدل شکست بخورد، AgentLoop سازوکار rollback یا idempotency ندارد.
   - بنابراین مسئلهٔ تکرار اجرای مأموریت پس از شکست همچنان باید در لایهٔ مدیریت مأموریت/Receiver حل شود؛ اجرای مجدد کورکورانه امن فرض نمی‌شود.

6. **نقطهٔ اتصال در main.py**
   - `main.py` اکنون Workspace، FileTools، test services، Registry، Dispatcher و AgentLoop را می‌سازد و چهار ابزار `read_file`، `list_files`، `apply_patch` و `run_tests` را ثبت می‌کند.
   - provider فعلی فقط OpenRouter و Gemini است؛ مسیر Ollama هنوز در composition root وجود ندارد.
   - Workspace پیش‌فرض `~/ilan-lab/ilan-workspace` است و با `ilan-workbench` متفاوت است. مقصد نهایی Workspace باید صریح و واحد پیکربندی شود.
   - callbackهای مجوز مدیریتی و Patch از `input()` ترمینال استفاده می‌کنند؛ این الگو برای اجرای غیرتعاملی از Telegram مناسب نیست.
   - System Prompt فعلی می‌گوید هر Patch نیازمند تأیید صریح کاربر است؛ این عبارت با تصمیم ثبت‌شدهٔ بخش ۳۳ دربارهٔ Patchهای داخل مأموریت‌های مشخص ایگور ناسازگار است و هنگام اتصال Telegram باید اصلاح شود.
   - `main.py` در حال حاضر CLI تعاملی است و حلقهٔ دریافت `input()` دارد؛ Receiver تلگرام باید ورودی مأموریت را به سرویس/عامل بدهد، نه اینکه به این حلقهٔ CLI وابسته شود.

### پیامدهای طراحی برای MVP

- AgentLoop موجود نامزد مناسبی برای هستهٔ چرخهٔ مدل و ابزار است؛ بازنویسی آن از صفر توجیه نشده است.
- client جدید Ollama باید قرارداد `chat(messages, tools=...)` و شکل پاسخ سازگار با `choices[0].message` را فراهم کند.
- composition root باید از حلقهٔ CLI جدا شود تا Receiver بتواند سرویس را درون همان فرایند فراخوانی کند.
- مدیریت درخواست Telegram، شناسهٔ مأموریت، وضعیت اجرا، نتیجهٔ نهایی و سیاست جلوگیری از اجرای تکراری باید بیرون از AgentLoop تعریف شود.
- مسیر Workspace، رفتار مجوزهای مدیریتی، اجرای تست‌ها و سیاست Patch باید پیش از اتصال عملی Telegram روشن و آزموده شوند.
- این ثبت صرفاً مستندکردن بررسی است؛ در این مرحله هیچ کد، تنظیمات، فایل SQLite، Firewall یا نصب وابستگی تغییر داده نشده است.

### مواردی که هنوز باید در طراحی/اعتبارسنجی روشن شوند

- قرارداد دقیق Tool Call مورد انتظار Ollama برای مدل `gpt-oss-20b-local:latest` و سازگاری آن با تعریف ابزارهای فعلی.

## ۳۸. بررسی WorkspaceBoundary و FileTools برای میزکار مستقل

**منبع بررسی:** دو فایل کد ارسالی کاربر در تاریخ ۲۰۲۶-۱۱-۲۰، شامل پیاده‌سازی `WorkspaceBoundary` و `FileTools`.

### یافته‌های قطعی از کد

1. **WorkspaceBoundary**
   - سیستم‌عامل را Linux و معماری را x86_64 یا aarch64 الزام می‌کند و پشتیبانی `openat2` را هنگام ساخت نمونه بررسی می‌کند.
   - مسیر ریشه را با `expanduser().resolve()` canonical می‌کند و الزام می‌کند ریشه از قبل وجود داشته و پوشه باشد.
   - مسیر مطلق، مسیر دارای NUL و پیمایش والد با `..` را رد می‌کند.
   - برای بازکردن مسیرهای داخل Workspace از `openat2` با `RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS` استفاده می‌کند؛ Symlinkهای داخلی مجازند، اما مسیرهای خارج‌شونده از ریشه رد می‌شوند.
   - نوشتن فایل از طریق فایل موقت و جایگزینی/لینک اتمیک انجام می‌شود؛ مقصد Symlink و مقصد غیر regular-file برای جایگزینی پذیرفته نمی‌شوند.

2. **FileTools**
   - ریشهٔ Workspace را خودش تعیین نمی‌کند؛ شیء `workspace` را در سازنده دریافت و نگه‌داری می‌کند.
   - فهرست‌کردن و خواندن فایل از `workspace.open_file` استفاده می‌کنند.
   - نوشتن فایل و ثبت Patch از `workspace.write_atomic` استفاده می‌کنند.
   - بنابراین در خود این کلاس hard-code مستقلی برای مسیر قدیمی `ilan-workspace` مشاهده نشد؛ مرز واقعی عملیات به نمونهٔ `WorkspaceBoundary` تزریق‌شده وابسته است.

### نتیجه برای تصمیم بخش ۳۷

- از نظر طراحی این دو کلاس، انتخاب `~/ilan-lab/ilan-workbench/workspace` به‌عنوان ریشهٔ Workspace با الگوی تزریق‌شدهٔ فعلی سازگار به نظر می‌رسد.
- برای این دو کلاس، بازنویسی یا تغییر منطق امنیتی صرفاً به‌خاطر تغییر مسیر لازم به نظر نمی‌رسد.
- تغییر مسیر باید در composition root یعنی محل ساخت `WorkspaceBoundary` انجام شود؛ تنظیم `ILAN_WORKSPACE` نیز باید به همین مسیر اشاره کند یا مقدار پیش‌فرض آن اصلاح شود.
- این بررسی کد است، نه آزمون اجرایی؛ هنوز نمونهٔ واقعی روی مسیر جدید ساخته نشده و آزمون امنیتی/عملی انجام نشده است.

### ریسک فنی مستقل در apply_patch

- `FileTools.apply_patch` فایل را می‌خواند و SHA-256 را با `expected_sha256` مقایسه می‌کند؛ پس از ساخت محتوای جدید، آن را با `write_atomic` می‌نویسد.
- بین بررسی هش و نوشتن نهایی، مقایسهٔ اتمیک نسخهٔ فعلی فایل با هش مورد انتظار دیده نمی‌شود.
- در نتیجه اگر فرایند دیگری در این فاصله همان فایل را تغییر دهد، امکان بازنویسی تغییر هم‌زمان وجود دارد. این ریسک به انتخاب مسیر Workspace وابسته نیست و باید پیش از اتکای عملی به Patchهای هم‌زمان بررسی شود.
- فعلاً هیچ تغییری برای رفع این ریسک اعمال نشده است.

### موارد هنوز بررسی‌نشده

- پیاده‌سازی wrapperهای ثبت چهار ابزار `list_files`، `read_file`، `apply_patch` و `run_tests` هنوز در این مرحله دریافت/بررسی نشده است؛ بنابراین تأیید نهایی مسیر و سیاست هر چهار ابزار منوط به بررسی آن فایل‌هاست.
- وجود واقعی و مجوزهای مسیر `ilan-workbench/workspace` در WSL در این نوبت دوباره آزموده نشده است.
- هیچ کد، فایل محیطی، Workspace یا داده‌ای تغییر نکرده است.

**منبع بررسی:** کدهای ارسالی کاربر در تاریخ ۲۰۲۶-۱۱-۲۰ برای چهار Wrapper و تست‌های زیر:

### ۳۹.۳. Wrapper مربوط به run_tests

- شناسه‌های پروفایل هنگام ثبت ابزار از `profile_registry.list_profiles()` خوانده و در schema به‌صورت `enum` قرار داده می‌شوند.

- بنابراین امن‌بودن اجرای تست را نمی‌توان از این Wrapper نتیجه گرفت؛ کنترل واقعی در `test_service`، پروفایل‌ها و Executor قرار دارد.
- فهرست enum در schema یک راهنمای قرارداد ابزار است؛ تا وقتی اعتبارسنجی سمت Dispatcher/Service اثبات نشده، نباید آن را به‌تنهایی کنترل امنیتی قطعی فرض کرد.

### ۳۹.۴. آنچه تست‌های ارسالی واقعاً اثبات می‌کنند

**`test_run_tests.py`**
- تست اول ثابت می‌کند schema ابزار، شناسهٔ پروفایل ثبت‌شده را در enum قرار می‌دهد و فیلد `profile_id` را اجباری و سایر فیلدهای اضافی را ممنوع اعلام می‌کند.
- تست دوم ثابت می‌کند Wrapper شناسهٔ پروفایل و همان شیء Workspace دریافتی را به `test_service.execute` پاس می‌دهد.
- این تست‌ها رفتار Wrapper را می‌آزمایند؛ محدودشدن اجرای فرایند به Workspace یا امنیت Docker را اثبات نمی‌کنند.

**`test_workspace.py`**
- مسیر خالی و `None`، مسیر مطلق و پیمایش والد `..` را برای `open_file` رد می‌کند.
- بازکردن ریشهٔ `.` به‌عنوان directory را بررسی می‌کند.
- در این فایل تست ارسالی، آزمون صریحی برای Symlink داخلی، Symlink خروجی، نوشتن اتمیک، رقابت هم‌زمان، مسیر ریشهٔ واقعی Workbench یا رفتار در برابر تغییر مسیر در زمان اجرا دیده نمی‌شود. این موارد ممکن است در تست‌های دیگر باشند؛ از این فایل به‌تنهایی نمی‌توان دربارهٔ آن‌ها نتیجه گرفت.

**`test_docker_executor.py`**
- تست‌ها نشان می‌دهند Authorization باید پیش از شروع Docker انجام شود.
- در صورت رد مجوز، `subprocess.Popen` نباید فراخوانی شود.

**`test_authorization.py`**
- تأیید callback باید پیش از اجرای `sudo -v` انجام شود.
- در صورت رد callback، sudo نباید اجرا شود.
- خطای احراز sudo و نبودن فرمان sudo به‌صورت خطاهای مشخص گزارش می‌شوند.
- این تست‌ها اثبات نمی‌کنند که فرمان Docker بعدی با همان هویت/مجوز محدود اجرا می‌شود یا اینکه `sudo -v` به‌تنهایی مرز امنیتی ایجاد می‌کند.

### ۳۹.۵. ارزیابی موقت انتقال به Workbench

- سه Wrapper فایل از نظر تزریق وابستگی با تصمیم بخش ۳۷ و بررسی بخش ۳۸ سازگارند؛ اگر `FileTools` از `WorkspaceBoundary` با ریشهٔ `~/ilan-lab/ilan-workbench/workspace` ساخته شود، Wrapperها مسیر را به ریشهٔ دیگری تغییر نمی‌دهند.

- فعلاً شواهد کافی برای تأیید امنیت اجرای تست یا تأیید کامل انتقال وجود ندارد.
- تغییر در Wrapperها یا `WorkspaceBoundary` در این مرحله توصیه نمی‌شود؛ گام بعدی باید بررسی پیاده‌سازی Service، Profile Registry و Docker Executor باشد.

5. پس از دریافت این کدها، طراحی آزمون پذیرش برای اجرای pytest در `ilan-workbench/workspace` و تلاش برای دسترسی به مسیر خارج از آن انجام شود.

## ۴۰. بررسی زنجیره اجرای تست، پروفایل‌ها و DockerTestExecutor

**منبع بررسی:** کدهای ارسالی کاربر در تاریخ ۲۰۲۶-۱۱-۲۰ شامل:
- `agent/loop.py` از طریق تست‌های `test_agent_loop.py` (فقط تست‌ها ارائه شده‌اند، نه پیاده‌سازی AgentLoop)
- `core/test_profiles.py`
- `core/test_execution.py` (کلاس `TestExecutionService`)
- `core/test_executor.py`
- `core/docker_executor.py` (کلاس `DockerTestExecutor`)

### ۴۰.۱. زنجیرهٔ وابستگی اجرای تست

بر اساس کدهای ارائه‌شده، زنجیرهٔ مورد انتظار چنین است:

`run_tests Wrapper → TestExecutionService.execute → TestProfileRegistry.get → ExecutionRequest → TestExecutor.execute → DockerTestExecutor.execute`

- `TestExecutionService` نوع Registry، Workspace و Limits را بررسی می‌کند.
- پروفایل با شناسهٔ ثبت‌شده resolve می‌شود.
- مسیر `workspace.root` به `ExecutionRequest.workspace_path` منتقل می‌شود.
- Executor از طریق قرارداد `TestExecutor` تزریق می‌شود؛ بنابراین این کد به‌تنهایی ثابت نمی‌کند در composition root یا `main.py` حتماً `DockerTestExecutor` واقعی تزریق شده است.
- تطبیق Executor واقعی با مسیر اجرا باید در composition root بررسی شود.

### ۴۰.۲. اعتبارسنجی پروفایل

- `TestProfile` یک dataclass تغییرناپذیر است.
- `profile_id` با الگوی نام محدود اعتبارسنجی می‌شود.
- `command` باید tuple غیرخالی از رشته‌های غیرخالی و بدون NUL باشد.
- `working_directory` باید مسیر نسبی POSIX باشد؛ مسیر مطلق، `..`، بک‌اسلش و NUL رد می‌شوند.
- `timeout_seconds` باید عدد صحیح مثبت باشد.
- پروفایل پیش‌فرض `pytest` فرمان `python -m pytest -q`، دایرکتوری `.` و timeout برابر ۱۲۰ ثانیه دارد.
- این اعتبارسنجی مانع مسیرهای سادهٔ traversal در working_directory می‌شود؛ ولی اعتبارسنجی پروفایل به‌تنهایی sandbox اجرای فرمان نیست. اعتماد به منبع ثبت پروفایل و محدودیت فرمان‌های قابل ثبت همچنان مهم است.

### ۴۰.۳. کنترل‌های Docker که در کد مشاهده شدند

`DockerTestExecutor`:
- Workspace را با `resolve(strict=True)` به مسیر واقعی تبدیل می‌کند و وجود پوشه را بررسی می‌کند.
- مسیر working directory را resolve می‌کند و با `is_relative_to(workspace)` بررسی می‌کند که مقصد نهایی داخل Workspace باشد.
- پیش از اجرای Docker، `authorization_manager.authorize` را فراخوانی می‌کند.
- کانتینر را با `--network none` اجرا می‌کند.
- ریشهٔ فایل‌سیستم کانتینر را `--read-only` می‌کند و `/tmp` را به‌صورت tmpfs قابل‌نوشتن mount می‌کند.
- Workspace را با bind mount فقط‌خواندنی در `/workspace` قرار می‌دهد.
- تمام Linux capabilities را حذف می‌کند و `no-new-privileges` را فعال می‌کند.
- محدودیت PID، حافظه، swap و CPU اعمال می‌کند.
- شناسهٔ کاربر و گروه میزبان را به کانتینر منتقل می‌کند.
- برای اجرا timeout و سقف مجموع خروجی stdout/stderr دارد.
- فرمان با آرایهٔ آرگومان‌ها به `subprocess.Popen` داده می‌شود، نه با یک رشتهٔ shell؛ در همین قطعه استفادهٔ مستقیم از `shell=True` دیده نمی‌شود.

این کنترل‌ها دفاع در عمق مناسبی ایجاد می‌کنند، اما به‌تنهایی اثبات ایزوله‌سازی کامل Docker یا امن‌بودن image و daemon نیستند.

### ۴۰.۴. ریسک‌ها و ابهام‌های باز

1. **تغییر مسیر بین بررسی و mount (TOCTOU):** مسیر Workspace و working directory قبل از مجوز resolve می‌شوند، اما Docker بعداً مسیر host را mount می‌کند. اگر عامل دیگری بتواند در این فاصله مسیر یا اجزای والد را جابه‌جا یا جایگزین کند، بررسی قبلی لزوماً مسیر mountشده را تضمین نمی‌کند. شدت این ریسک به مالکیت و مجوزهای دایرکتوری‌های والد و مدل دسترسی محلی بستگی دارد.
2. **اعتماد به Docker image:** نام پیش‌فرض `ilan-test:0.1` یک tag است، نه digest تغییرناپذیر. اگر image محلی موجود نباشد، رفتار pull پیش‌فرض Docker و منبع image باید روشن شود. تأیید کاربر فعلاً نام tag را نمایش می‌دهد، نه digest محتوای image را.
3. **فایل‌سیستم فقط‌خواندنی و pytest:** Workspace به‌صورت read-only mount شده است. pytest و ابزارهای Python ممکن است برای cache یا فایل‌های جانبی در Workspace بنویسند. `/tmp` قابل‌نوشتن است، اما در کد مشاهده‌شده `PYTHONDONTWRITEBYTECODE` یا انتقال cache pytest به `/tmp` تنظیم نشده است. باید با image و پروژهٔ واقعی آزمایش شود؛ ممکن است فقط warning ایجاد کند یا بعضی تست‌ها را مختل کند.
4. **محدودیت زمان:** deadline از پیش از شروع Docker CLI محاسبه می‌شود و timeout شامل زمان راه‌اندازی Docker نیز هست. این رفتار باید به‌عنوان timeout کل عملیات مستند و تست شود.
5. **پاک‌سازی کانتینر:** پس از timeout یا عبور از سقف خروجی، `kill` و سپس `rm` فراخوانی می‌شوند؛ خطاهای `_docker_control` نادیده گرفته می‌شوند. باید مشخص شود در شکست کنترل Docker چه تضمینی برای پاک‌سازی باقی می‌ماند.
6. **منبع مجوز:** `DockerTestExecutor` از `docker_prefix=("sudo", "-n", "docker")` استفاده می‌کند و AuthorizationManager نیز پیش از آن مجوز می‌گیرد. تست‌های موجود تقدم authorize بر شروع Docker را بررسی می‌کنند، اما سیاست واقعی sudoers، ماندگاری credential و اختیار کاربر اجرای Python باید در محیط هدف بررسی شود.
7. **سطح دسترسی کانتینر:** گزینه‌های ارائه‌شده کنترل‌های مفیدی هستند، اما در این قطعه محدودیت‌های دیگری مانند seccomp profile سفارشی، AppArmor/SELinux policy، کنترل deviceها، محدودیت mountهای اضافی و pin کردن image به digest صریحاً پیکربندی نشده‌اند. این موارد را نباید بدون بررسی تنظیمات پیش‌فرض میزبان، غایب یا امن فرض کرد.
8. **نوشتن نتایج تست:** Workspace read-only است؛ بنابراین اگر در آینده ایلان باید گزارش یا artifact تست را در Workspace ذخیره کند، باید مسیر خروجی جداگانه و کنترل‌شده‌ای طراحی شود، نه اینکه mount اصلی بی‌دلیل writable شود.

### ۴۰.۵. تست‌های AgentLoop

- تست‌های ارسالی نشان می‌دهند پاسخ عادی با یک فراخوانی مدل پایان می‌یابد.
- در سناریوی tool call، Dispatcher فراخوانی می‌شود و مدل برای پاسخ نهایی دوباره فراخوانی می‌شود.
- خطای API در نمونهٔ تست‌شده retry نمی‌شود.
- سقف سه فراخوانی مدل در تست مربوطه رعایت می‌شود و در سناریوی تکرار tool call، دو بار Dispatcher اجرا می‌شود.
- این تست‌ها رفتار حلقهٔ مکالمه و سقف دورها را بررسی می‌کنند؛ اعتبارسنجی schema ابزار، مجوزدهی، محدودسازی مسیر یا ایزوله‌سازی اجرای ابزار را اثبات نمی‌کنند.
- چون کد پیاده‌سازی `AgentLoop` و Dispatcher ارائه نشده، دربارهٔ جزئیات داخلی آن‌ها نتیجه‌گیری قطعی نمی‌شود.

### ۴۰.۶. ارزیابی موقت انتقال به Workbench

- `TestExecutionService` مسیر `workspace.root` را به Executor منتقل می‌کند؛ بنابراین از نظر تزریق ریشه، با الگوی Workspace جدید سازگار است.
- `DockerTestExecutor` مسیر داده‌شده را resolve می‌کند و working directory را از نظر قرارگیری درون Workspace می‌سنجد.
- اجرای تست در کانتینر با mount فقط‌خواندنی و شبکهٔ غیرفعال انجام می‌شود.
- با وجود این، تأیید نهایی انتقال منوط به بررسی composition root و آزمون‌های عملی در محیط هدف است؛ به‌خصوص برای اطمینان از اینکه Executor واقعی همین DockerTestExecutor است و Workspace مورد استفاده همان `ilan-workbench/workspace` است.
- در این مرحله هیچ کدی تغییر نکرده و هیچ تستی توسط ایگور اجرا نشده است.

### ۴۰.۷. گام‌های بعدی

2. بررسی اینکه آیا Executor واقعی همان `DockerTestExecutor` است و image و limits چگونه پیکربندی می‌شوند.
3. بررسی سیاست مجوز sudo و منبع/نسخهٔ Docker image.
4. طراحی تست عملی: اجرای pytest در Workspace جدید، بررسی cache/bytecode، رد working directory دارای Symlink خروجی، و آزمون اینکه کانتینر نمی‌تواند در Workspace بنویسد یا به شبکه دسترسی پیدا کند.
5. سپس تصمیم دربارهٔ حداقل تغییر لازم برای انتقال و ثبت آزمون‌های پذیرش.

### ۴۰.۸. وضعیت تغییرات

- تست‌ها در این مرحله توسط ایگور اجرا نشده‌اند.
- هیچ کدی، تنظیمی، مجوزی، image یا داده‌ای تغییر نکرده است.

## ۴۱. بررسی Composition Root در `main.py` و اتصال واقعی Bootstrap

**منبع بررسی:** نسخهٔ کامل `main.py` که کاربر در تاریخ ۲۰۲۶-۱۱-۲۰ ارسال کرد. این بخش بررسی ایستای کد است؛ اجرای برنامه یا تست‌ها در این مرحله انجام نشده است.

### ۴۱.۱. مسیر Workspace در زمان ساخت

- مسیر از متغیر محیطی `ILAN_WORKSPACE` خوانده می‌شود؛ در صورت نبودن آن، مقدار پیش‌فرض `~/ilan-lab/ilan-workspace` است.
- `expanduser()` اجرا می‌شود، سپس پوشه با `mkdir(parents=True, exist_ok=True)` ساخته می‌شود و `WorkspaceBoundary` روی همان مسیر ساخته می‌شود.
- بنابراین در کد فعلی، مسیر پیش‌فرض `ilan-workbench/workspace` نیست. مقدار محیطی می‌تواند مسیر را override کند، اما مقدار واقعی آن در زمان اجرای برنامه از متن `main.py` معلوم نیست.
- `WorkspaceBoundary` شیء واحدی است که به `FileTools` تزریق می‌شود و همان شیء نیز به Wrapper ابزار `run_tests` داده می‌شود. ریشهٔ نهایی و canonical به رفتار داخلی `WorkspaceBoundary` وابسته است؛ چاپ `workspace_path` در انتها لزوماً همان نمایش canonical ریشه نیست.

### ۴۱.۲. اتصال ابزارهای فایل

- `FileTools(workspace)` با همان `WorkspaceBoundary` ساخته می‌شود.
- `register_read_file`، `register_list_files` و `register_apply_patch` همگی همان `file_tools` را دریافت می‌کنند.
- در نتیجه، از نظر dependency injection این سه ابزار ریشهٔ مستقل دیگری در `main.py` دریافت نمی‌کنند و به مرز Workspace داخل `FileTools` وابسته‌اند.
- تأیید Patch از callback مستقل `request_patch_approval` می‌آید؛ این callback پیش‌نمایش مسیر و diff را در ترمینال نشان می‌دهد و فقط پاسخ `y/yes` را تأیید می‌داند.

### ۴۱.۳. اتصال واقعی اجرای تست

- رجیستری پروفایل با `create_default_test_profile_registry()` ساخته می‌شود.
- محدودیت‌های سراسری در این فایل برابر timeout برابر ۱۲۰ ثانیه، حافظهٔ ۵۱۲ MiB و CPU برابر ۱ هسته تنظیم شده‌اند.
- `AuthorizationManager` با callback به نام `request_authorization` ساخته می‌شود.
- همان manager به `DockerTestExecutor` تزریق می‌شود.
- همان Executor به `TestExecutionService` تزریق می‌شود؛ بنابراین در مسیر ساختی که این `main.py` تعریف می‌کند، Executor واقعی و انتخاب‌شده `DockerTestExecutor` است، نه صرفاً یک Protocol یا Mock.
- `register_run_tests`، همان `test_service`، همان `workspace` و همان `profile_registry` را دریافت می‌کند.
- زنجیرهٔ اتصال در این Composition Root چنین است: `run_tests Wrapper → TestExecutionService → DockerTestExecutor`.
- این تأیید مربوط به wiring کد است؛ اجرای واقعی Docker، صحت محیط daemon، image و مجوزهای سیستم‌عامل هنوز با این بررسی اثبات نشده‌اند.

### ۴۱.۴. دو مسیر تأیید مجزا

- `request_patch_approval` برای تأیید اعمال تغییر فایل است.
- `request_authorization` برای درخواست مجوز مدیریتی است و به `AuthorizationManager` متصل شده است.
- این دو callback از نظر هدف و محل استفاده مجزا هستند و نباید تأیید Patch را معادل مجوز اجرای Docker دانست.
- متن callback مجوز مدیریتی فقط عملیات متنی را در ترمینال نمایش می‌دهد و پاسخ مثبت را می‌پذیرد؛ معنای دقیق و جزئیات عملیات از قرارداد `AuthorizationManager` و متن ارسالی Executor می‌آید.
- از این فایل به‌تنهایی نمی‌توان نتیجه گرفت هر اجرای ابزار نیازمند تأیید کاربر است؛ تأیید Patch و مجوز Docker دو مسیر مشخص‌اند و سایر ابزارها callback تأیید جداگانه‌ای در این Composition Root ندارند.

### ۴۱.۵. Registry، Dispatcher و AgentLoop

- چهار ابزار `read_file`، `list_files`، `apply_patch` و `run_tests` در یک `ToolRegistry` ثبت می‌شوند.
- یک `ToolDispatcher` با همان Registry ساخته می‌شود.
- انتخاب مدل از `ILAN_MODEL_PROVIDER` انجام می‌شود و در این فایل فقط `openrouter` و `gemini` پشتیبانی شده‌اند؛ مقدار پیش‌فرض `openrouter` است.
- هیچ انتخاب مستقیم Ollama یا مدل محلی در این Composition Root مشاهده نمی‌شود. تنظیمات مدل محلی Bridge نباید به این AgentLoop تعمیم داده شود.
- `AgentLoop` همان model client، همان registry و همان dispatcher را دریافت می‌کند.
- متن system prompt محدودیت‌هایی را به ایلان اعلام می‌کند، از جمله ممنوعیت ادعای موفقیت بدون نتیجهٔ ابزار و ممنوعیت اجرای arbitrary shell command؛ اما system prompt به‌تنهایی کنترل امنیتی اجرایی نیست. محدودیت واقعی از ابزارهای ثبت‌شده و کنترل‌های سمت Wrapper، Dispatcher و سرویس‌ها حاصل می‌شود.

### ۴۱.۶. مدیریت خطا و چرخهٔ عمر Workspace

- حلقهٔ مکالمه خطاهای `OpenRouterError` و `GeminiError` را جداگانه می‌گیرد و صریحاً اعلام می‌کند retry خودکار انجام نمی‌شود.
- سایر خطاها در حلقه با عنوان `Runner error` چاپ می‌شوند و حلقه برای پیام بعدی ادامه می‌یابد.
- `workspace.close()` در `finally` قرار دارد و پس از خروج از حلقه یا خطای بعدی در بلوک محافظت‌شده اجرا می‌شود.
- ساخت مسیر و `WorkspaceBoundary` پیش از ورود به `try` انجام شده است؛ بنابراین خطاهای این مرحله تحت مدیریت خطای حلقه یا `finally` قرار نمی‌گیرند. در صورت شکست ساخت Boundary، هنوز شیء Workspace ساخته‌شده‌ای وجود ندارد که نیاز به بستن داشته باشد.
- مسیر چاپ‌شده در پیام آماده‌بودن، متغیر `workspace_path` است؛ برای گزارش دقیق ریشهٔ canonical بهتر است مقدار `workspace.root` نیز در اجرای عملی ثبت یا مقایسه شود، اگر این property در پیاده‌سازی Workspace موجود است.

### ۴۱.۷. اختلاف مهم با هدف Workbench و موارد باز

1. **ریشهٔ واقعی Workbench:** مسیر پیش‌فرض هنوز `~/ilan-lab/ilan-workspace` است، در حالی که هدف انتقال پیش‌تر `~/ilan-lab/ilan-workbench/workspace` مطرح شده بود. پیش از هر تغییر باید مقدار واقعی `ILAN_WORKSPACE` در محیط اجرای ایلان بررسی شود.
2. **اعتبارسنجی Dispatcher:** این فایل فقط نشان می‌دهد Dispatcher با Registry ساخته شده است؛ رفتار parse، schema validation، رد آرگومان‌های اضافی و مدیریت خطا باید از پیاده‌سازی فعلی `tools/dispatcher.py` بررسی شود. نباید از روی این Composition Root آن‌ها را فرض کرد.
3. **اتصال به محیط اجرا:** کد نشان می‌دهد مجوز مدیریتی از callback تعاملی ترمینال گرفته می‌شود. اگر برنامه در محیطی بدون ورودی تعاملی اجرا شود، مسیر درخواست مجوز ممکن است متوقف یا ناموفق شود؛ این رفتار باید در محیط واقعی سنجیده شود.
4. **اعتماد به تنظیمات محیطی:** `ILAN_WORKSPACE` و `ILAN_MODEL_PROVIDER` ورودی‌های محیطی‌اند. مقدار نهایی آن‌ها و محل تنظیمشان در اجرای واقعی هنوز مشاهده نشده است.
5. **امنیت فراتر از wiring:** اتصال صحیح Workspace و Docker Executor به‌تنهایی امنیت کامل را اثبات نمی‌کند؛ ریسک‌های image، Docker daemon، TOCTOU، cleanup، سیاست sudo و آزمون عملی محدودیت‌ها که در بخش ۴۰ ثبت شده‌اند، باز می‌مانند.

### ۴۱.۸. جمع‌بندی موقت

- اتصال `FileTools` به `WorkspaceBoundary` و اتصال `TestExecutionService` به `DockerTestExecutor` در Composition Root ارسالی تأیید شد.
- چهار ابزار مورد انتظار در یک Registry ثبت شده و همان Registry به Dispatcher و AgentLoop داده شده است.
- مهم‌ترین اختلاف فعلی با طرح انتقال، مسیر پیش‌فرض Workspace است؛ هنوز `ilan-workbench/workspace` در `main.py` به‌عنوان پیش‌فرض تثبیت نشده است.
- این بررسی فقط wiring و ساختار کد را تأیید می‌کند؛ هیچ تست یا اجرای Docker در این مرحله انجام نشده و امنیت کامل یا انتقال عملی به Workbench تأیید نشده است.
- هیچ کدی یا تنظیم محیطی در این مرحله تغییر داده نشده است.

### ۴۱.۹. گام بعدی پیشنهادی

1. مقدار واقعی `ILAN_WORKSPACE` هنگام اجرای ایلان و مسیر canonical گزارش‌شده توسط Workspace.

- تا حد ممکن از اجزای موجود `ilan-bootstrap` استفاده شود؛ بازنویسی یا بازطراحی از صفر در دامنهٔ این مرحله نیست.

- این تصمیم به معنی تأیید امنیت کامل اجزای موجود نیست؛ بررسی‌های امنیتی عمیق‌تر به مرحلهٔ تکمیل و سخت‌سازی منتقل می‌شوند.

### ۴۲.۲. ساختار حداقلی میزکار

ساختار هدف اولیه:

```text
ilan-workbench/
├── inbox/       # ورودی‌ها و مأموریت‌ها
```

این ساختار، هدف نسخهٔ حداقلی است؛ وجود یا اتصال عملی همهٔ پوشه‌ها در برنامه تا زمان آزمون تأیید نمی‌شود.

### ۴۲.۳. ابزارهای نسخهٔ اول

در نسخهٔ اول فقط چهار ابزار موجود نگه داشته می‌شوند:
- `list_files`: فهرست‌کردن فایل‌های Workspace.
- `read_file`: خواندن فایل‌های Workspace.
- `apply_patch`: پیشنهاد و اعمال Patch پس از تأیید صریح کاربر.

افزودن ابزارهایی مانند `search_files`، `search_text`، `write_file` و `get_diff` فعلاً به تعویق می‌افتد. همچنین حافظهٔ پیچیده، خودگردانی گسترده و قابلیت‌های تکمیلی پیش‌نیاز نسخهٔ اول نیستند.

### ۴۲.۴. معیار پذیرش نسخهٔ اول

1. فهرست‌کردن فایل‌های پروژه.

3. تحلیل و پیشنهاد تغییر کوچک و مستدل.
